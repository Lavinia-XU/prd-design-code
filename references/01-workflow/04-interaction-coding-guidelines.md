## 1. 概览

交互补齐与编码指导规范用于把页面设计说明转化为AI编程工具可执行的前端Demo实现要求。Demo重点是让用户直观看到需求对应的页面、流程、交互和基础逻辑限制，不需要实现真实后端接口、数据库、鉴权或复杂算法，除非用户明确要求。

这份规范分成三大类：

- 第一部分：交互逻辑补齐规则，用于把需求补成可设计、可展示、可演示的页面规则。
- 第二部分：编码指导规则，用于把已经形成的页面说明转成可执行的AI Coding约束，并强化代码复用优先级。
- 第三部分：Skill执行与交付规则，用于约束待确认问题、Coding推进、HTML与Coding衔接以及最终交付节奏。

## 2. 第一部分：交互逻辑补齐规则

### 2.1 关键交互说明来源与补齐原则

页面关键交互说明必须从五类信息中综合生成：

1. 需求资料：用户明确提到的操作、流程、状态、限制、字段、按钮和业务结果。
2. 业务设计Skill：产品介绍、页面导航结构、页面说明、页面设计规范、同类功能交互、弹窗/抽屉习惯和菜单命名。
3. Demo代码环境：已有路由、菜单配置、相似页面、组件组织、Mock数据结构、状态管理和交互处理方式。
4. 通用设计库：仅在业务设计Skill未覆盖、未说清楚或用户未提供业务设计Skill时使用；先按需求命中的主题读取主题类设计文档作为框架级参考，再结合实际业务对字段配置、字段展示、操作和状态进行增删减；主题类设计未覆盖时，再用基础设计库中的页面类型、表格、表单、详情、Tab、二次确认、长表单、轻量配置入口和多层级下钻设计手法补充。
5. AI业务理解：基于业务目标、用户任务、页面容器类型和Demo可演示性进行合理补齐。

AI补齐可用于修正需求中缺失但从产品专业性、行业通用设计和用户体验友好程度看需要完善的内容，例如基础交互、前端状态、Demo逻辑限制、校验提示、空状态和异常反馈。补齐目标仅限于确保产品达到可用、易用和可演示，不得偏离需求设定范围做过多发挥，不得新增复杂业务能力。

每个关键交互至少说明：

| 说明项 | 写法要求 |
| ------ | -------- |
| 触发入口 | 用户从哪个页面、区块、按钮、字段、统计数字或链接触发 |
| 触发方式 | 点击、输入后查询、选择筛选项、勾选后批量操作、切换Tab等 |
| 打开容器 | 跳转页面、打开抽屉、打开弹窗、展示Popover/Tooltip、Toast提示等 |
| 页面反馈 | 当前页面如何变化，如表格刷新、按钮loading、区块展开、状态标签变化 |
| 数据变化 | Mock数据如何更新，如新增一行、修改当前行、状态变为已处置、列表移除 |
| 校验规则 | 必填、格式、范围、依赖关系、批量选择为空、未保存离开等 |
| 成功反馈 | 成功文案、关闭容器、刷新范围、返回位置 |
| 失败反馈 | 错误提示、保留输入、允许重试 |
| 状态联动 | 列表、统计卡片、详情状态、Tab数量是否同步变化 |
| 边界状态 | 空状态、搜索无结果、加载态、异常态、无权限态、长文本等 |

禁止只写“点击查看详情”“点击提交”“点击删除”这类结果不完整的描述。

### 2.2 筛选条件判定规则

当需求没有明确写出筛选条件时，AI 应根据表格字段语义自动补充右侧查询区；不要因为需求未提到筛选条件就默认不设置筛选，判断原则如下：

- 名称类字段，如名称、设备名、任务名、用户名称、策略名称，默认使用输入框进行关键字搜索。
- 状态类字段，如状态、启用状态、运行状态、告警级别、审批状态，默认使用下拉单选。
- 分类、枚举或归属类字段，如类型、分组、来源、区域、标签、级别、所属组织、所属项目，默认使用下拉单选；如果业务允许多条件组合，则改为下拉多选。
- 时间类字段，如创建时间、更新时间、开始时间、结束时间、触发时间，默认使用时间范围选择器或日期范围选择器。
- 对象关联类字段，如关联对象、所属设备、所属策略，默认使用搜索选择器或下拉选择器。
- 纯展示字段、备注字段、长文本字段、复杂配置字段、操作列和图标列，默认不进入查询区。
- 若表格字段不足以明确判断，优先补充 1 个名称搜索框、1 个状态下拉和 1 个时间范围选择器。
- 当筛选项超过 4 个，或筛选条件需要组合管理时，升级为高级搜索组件。
- 页面说明中必须写清哪些字段进入查询区、每个字段使用什么控件，以及是否需要升级为高级搜索组件。

### 2.3 搜索、筛选、重置、排序、分页

| 交互 | 必须说明 | Demo实现要求 |
| ---- | -------- | ------------ |
| 搜索 | 搜索字段、匹配方式、触发方式 | 基于Mock数据做模糊匹配或精确匹配 |
| 筛选 | 筛选项、选项范围、是否可组合 | 多个筛选条件应组合生效 |
| 重置 | 重置哪些条件 | 清空筛选项并恢复默认列表 |
| 排序 | 默认排序字段、可排序字段 | 至少体现默认排序；可排序字段需要可点击切换升降序 |
| 分页 | 每页数量、总数展示 | 数据量超过一页时展示分页 |

### 2.4 新增、编辑、查看

- 新增和编辑默认复用同一表单容器，除非字段或流程明显不同。
- 查看如果只是同一组信息的只读态，可复用表单只读状态；如果包含状态、关联策略、运行记录、告警统计等额外信息，应拆为抽屉详情页或下钻详情页。
- 表单提交前必须校验必填项、格式、取值范围和依赖关系。
- 提交成功后需要说明反馈方式：关闭弹窗/抽屉、刷新列表、更新当前行状态、Toast提示等。
- 提交失败时保留用户已填写内容，并展示错误提示。

### 2.5 删除、禁用、处置、批量操作

高影响操作必须说明二次确认：

| 操作 | 二次确认 | 常见文案 | Demo反馈 |
| ---- | -------- | -------- | -------- |
| 删除 | 必须 | 删除后数据不可恢复，确认删除？ | 删除成功后从列表移除或状态变更 |
| 禁用 | 必须 | 禁用后相关业务可能受影响，确认禁用？ | 状态变为已禁用 |
| 重启 | 必须 | 重启期间服务可能短暂不可用，确认重启？ | 展示操作中，再恢复状态 |
| 业务下线 | 必须 | 下线后业务访问可能受到影响，确认下线？ | 状态变为已下线或下线中 |
| 批量处置 | 必须 | 将对选中对象执行批量操作，确认继续？ | 批量更新状态或提示部分成功 |
| 未保存离开 | 必须 | 当前修改未保存，离开后不会生效，是否保存？ | 保存、放弃、继续编辑 |

高危操作可增加管理员密码、输入对象名称或二次勾选确认，但仅在业务确有风险时使用。

### 2.6 状态与边界规则

#### 2.6.1 基础状态

| 状态 | 出现场景 | 页面表现 | 操作建议 |
| ---- | -------- | -------- | -------- |
| 空状态 | 初始无数据 | 展示空状态文案和图标 | 提供新增或刷新入口 |
| 搜索无结果 | 查询条件无匹配 | 展示“暂无符合条件的数据” | 提供重置筛选 |
| 加载态 | 查询、筛选、切换页面 | 表格或内容区展示loading | 禁用重复点击 |
| 提交中 | 表单提交、批量操作 | 按钮loading | 防止重复提交 |
| 提交失败 | 网络异常或校验失败 | Toast或表单错误提示 | 保留已填写内容 |
| 无权限态 | 用户无操作权限 | 按钮置灰或隐藏 | 悬浮提示无权限原因 |

#### 2.6.2 极端情况

| 极端情况 | Demo体现方式 |
| -------- | ------------ |
| 长文本 | 单行省略，悬浮展示完整内容 |
| 数值为0 | 指标卡展示0，不隐藏卡片 |
| 字段为空 | 使用“-”或“暂无”展示，不留空白 |
| 数据量大 | 表格分页，每页10条或20条 |
| 状态很多 | 使用标签、筛选和排序帮助识别重点 |
| 高风险数据很多 | 默认按风险等级和发现时间排序 |
| 批量选择为空 | 点击批量操作时提示“请先选择数据” |
| 部分成功 | 批量操作后展示成功数和失败数 |

### 2.7 组件与样式建议

默认组件建议：

- 概览指标：卡片、数字、趋势或状态标签。
- 查询条件：筛选表单、输入框、下拉框、日期范围、重置按钮。
- 主数据：表格、分页、排序、行内操作。
- 中等复杂详情：抽屉详情页。
- 轻量表单：弹窗表单页。
- 中等复杂表单：抽屉表单页。
- 高危确认：弹窗二次确认。
- 状态表达：Tag、状态点、图标+文字。
- 长文本：Tooltip。
- 操作反馈：Message、Toast、Alert。

## 3. 第二部分：编码指导规则

### 3.1 代码复用优先级规则

Coding阶段以“复用优先、差异最小化、体验一致性”为原则。凡是已有页面、已有组件或已封装能力能够满足需求的，优先直接复用；仅在复用不足时做局部扩展；只有完全没有可复用基线时才新建实现。

复用优先级如下：

1. 先复用已打包组件，例如资产选择器、导入导出控件、通用筛选条、通用弹窗。
2. 再复用已开发页面的成熟模式，例如概览表格页、详情抽屉页、编辑表单页。
3. 再复用已有功能链路，例如导入、导出、批量操作、确认弹窗、状态更新。
4. 最后才做新增实现，并且只补现有基线不覆盖的差异部分。

复用判定标准：

- 直接复用：组件或页面完全可用，只替换数据或配置。
- 框架复用：布局、结构、交互模式复用，只改局部差异。
- 样式复用：视觉风格和排版沿用已有页面。
- 参考复用：只参考实现思路，不照搬代码。

### 3.2 代码环境结合规则

当存在Demo代码环境、用户指定代码范围、业务设计Skill提到参考模块或用户提到已有模块时，AI Coding指导必须结合代码结构生成。

重点读取并转化为Coding指导的内容：

- 路由和菜单配置：用于判断页面入口、导航路径和是否新增菜单或Tab。
- 相似页面实现：用于复用页面布局、表格工具栏、筛选表单、详情容器、弹窗和抽屉模式。
- 组件组织方式：用于说明应复用的组件、样式和交互反馈方式。
- Mock数据和状态结构：用于定义Demo数据字段、状态值、列表更新和筛选逻辑。
- 现有交互处理：用于沿用搜索、重置、分页、二次确认、Toast、loading和异常提示习惯。

如果代码与需求、业务设计Skill或通用设计库存在冲突，必须进入待确认问题，并在AI Coding指导中标记当前默认假设。不要把后端接口、数据库、任务调度等技术实现写成Demo页面功能。

### 3.3 Mock数据规则

Mock数据必须服务于Demo展示、逻辑验证和编码实现，不只是填满表格。

#### 3.3.1 列表数据

列表类页面至少提供10-15条Mock数据，覆盖：

- 主要状态：如正常、告警、离线、待处置、处理中、已处置。
- 主要类型：如高/中/低风险，启用/禁用，成功/失败。
- 至少1条长文本，用于验证省略和悬浮提示。
- 至少1条字段为空，用于验证空值展示。
- 至少1条高优先级或异常数据，用于默认重点展示。
- 如果有时间筛选，Mock数据应覆盖不同日期。

#### 3.3.2 表单数据

表单类Demo需要提供：

- 默认值。
- 下拉选项、单选项、复选项。
- 必填校验示例。
- 格式错误示例。
- 字段联动示例。
- 高级配置默认收起或展开规则。

#### 3.3.3 详情数据

详情类Demo需要提供：

- 对象信息卡片数据。
- 描述列表字段。
- 关联表格数据。
- 时间线或操作记录。
- 状态、风险、处置建议等用于帮助用户判断的信息。

### 3.4 AI Coding指导输出格式

HTML设计说明书中的AI Coding指导分为总览级和页面级两层：总览级写整体开发策略，页面级写单个页面的具体开发项。页面级指导继承总览级规则，不重复全局编码边界和一致性要求，只补充当前页面的复用对象、开发方式、差异内容和Mock特殊要求。

#### 3.4.1 总览 AI Coding指导

总览 AI Coding指导写在HTML设计说明书的总览部分，用于说明整个Demo的开发策略和边界。

| 输出项 | 说明 |
| --- | --- |
| 全局复用策略 | 说明本次Demo优先复用哪些已有页面、菜单模块、公共组件、功能链路或已打包能力。 |
| 全局Mock策略 | 说明整体Mock数据来源、结构复用方式、状态覆盖范围和是否沿用已有mock结构。 |
| 全局编码边界 | 说明不实现真实后端、数据库、鉴权、复杂算法、外部系统联调和本次范围外功能。 |
| 全局一致性要求 | 说明页面视觉、表格样式、按钮位置、弹窗/抽屉、反馈方式和组件调用方式必须与现有代码保持一致。 |
| 页面开发顺序 | 说明建议优先开发哪些页面，再开发哪些关联页面或配置页面。 |

#### 3.4.2 页面级 AI Coding指导

页面级 AI Coding指导写在每个页面说明中，用于说明当前页面的具体开发项。页面级指导应以开发项为单位输出，每个开发项需说明开发方式和开发描述；开发方式可为复用框架、直接引用、组件复用或全新开发。若存在业务设计Skill、业务设计文档或业务相关输入，应优先从其中查找页面、菜单模块、公共组件和功能链路的映射关系，再决定复用对象与开发方式。不要重复页面区块说明中的交互、状态和页面表现。

##### 开发项编码指导表

| 开发项 | 开发方式 | 开发描述 |
| --- | --- | --- |
|  
| 筛选搜索组件 | 复用框架 / 直接引用 / 组件复用 / 全新开发 | 说明使用哪个现有组件，以及是否需要特殊配置、校验或联动。 |

##### 页面级Mock数据要求

- 说明当前页面需要覆盖哪些状态、字段类型、异常值和边界场景。
- 说明是否复用已有mock结构，或需要补充新的数据字段。
- 说明列表、表单、详情页分别需要准备哪些数据。

##### 页面级输出形式

- 输出一份可直接执行的页面级Coding指导说明。
- 说明中必须包含开发项、开发方式和开发描述。
- 如有页面级mock特殊要求，在表格后补充说明。
- 最终目标是产出可运行Demo页面，或在现有项目中完成对应页面。

##### 示例

| 开发项 | 开发方式 | 开发描述 |
| --- | --- | --- |
| 页面框架 | 复用框架 | 复用资产管理概览页的整体布局和表格区块，仅替换页面标题、筛选项和列表字段。 |
| 导入/导出 | 直接引用 | 直接复用已有资产管理页的导入导出实现，只替换文案和接口参数。 |
| 资产选择弹窗 | 组件复用 | 直接调用已打包的资产选择器组件，按当前页面需要补充默认选中和回填字段。 |
| 筛选搜索组件 | 组件复用 | 复用现有筛选组件，增加资产名称、状态和时间范围三个筛选项。 |

##### 补充说明

- 如果某一项没有可复用基线，才标记为全新开发。
- 如果存在特殊参数、特殊校验或特殊交互差异，需要在开发描述里写清楚。

### 3.5 全局编码约束

#### 不需要实现的内容

- 不实现真实后端接口。
- 不实现数据库操作。
- 不实现鉴权或权限系统。
- 不实现复杂算法。
- 不实现外部系统联调。
- 不实现本次范围外功能。

#### 代码一致性要求

- 优先沿用现有页面视觉和布局。
- 优先复用现有按钮位置、反馈方式和交互习惯。
- 导入导出、资产选择器、筛选组件等优先沿用已有实现。
- 仅在现有实现不足时，才做局部差异化处理。

## 4. 第三部分：Skill执行与交付规则

### 4.1 待确认问题使用规则

待确认问题只保留会影响Demo闭环或Coding实现的问题，用于约束默认假设，避免把不确定内容写成事实。

仅保留以下问题：

- 导航与容器：新增菜单、复用菜单、Tab归属、页面/抽屉/弹窗/详情页选择。
- 用户旅程：入口、完成后的返回位置、审批/提交/处置流转和旅程卡点。
- 关键业务规则：状态流转、权限、高危校验、二次确认、批量操作。
- Coding实现：复用组件、Mock数据状态、与已有页面联动、是否读取指定模块。
- 关键需求缺失：目标用户、核心操作结果、状态定义、关键字段或列表对象。

问题优先控制在3-6个，最多10个；每个问题写清影响范围和当前默认假设。不阻断Demo闭环的问题按默认假设继续；阻断Demo成立的问题优先向用户确认。

### 4.2 Coding启动与确认规则

HTML设计说明书生成后，先提醒用户查看HTML页面内容；如用户提出页面结构、字段、交互、状态、文案或说明修改，先更新设计说明JSON并重新生成最新HTML，再基于最新HTML输出Coding计划。

Coding计划只确认开发实现方式，不重新确认业务设计内容。计划需覆盖：

- 导航结构：新增路由、新增菜单、复用菜单、Tab或页面入口。
- 开发页面：页面ID、页面名称、页面类型和容器形式。
- 复用对象：参考页面、代码模块、组件、样式、Mock数据、状态管理或功能链路。
- 新增内容：需要新增编码的页面、交互、状态、Mock数据或前端逻辑。
- 开发顺序：先父级主页面，再新增、编辑、详情、弹窗或抽屉等子页面。

用户明确同意后才开始Coding。Coding时需综合原始需求、用户确认内容、业务设计Skill、通用设计库、功能点设计、已有代码和HTML设计说明书；HTML不是机械执行稿，若与更高优先级依据冲突，按更高优先级修正并简要说明原因。

### 4.3 页面开发执行规则

按HTML左侧页面目录和页面层级拆分Coding任务，先开发父级主页面，再开发子页面、弹窗或抽屉；一个页面完成并自检后，再开始下一个页面，避免入口、状态联动和Mock数据不一致。

每页开发前确认：

1. 当前页面ID、页面名称、页面类型和容器形式。
2. 页面类型是否需要读取 [页面类型与页面元素说明](../04-design-basics/01-page-types.md)。
3. 是否有相似页面、已有组件、已有功能链路或Mock结构可复用。
4. 当前页面必须还原的区块、字段、按钮顺序、状态、边界和页面级AI Coding指导。
5. 当前页面是否存在用户否定后需要同步删除代码的补齐内容。

每页开发后检查：

1. 页面结构、区块顺序、容器形态是否与HTML说明书和页面类型要求一致。
2. 筛选搜索、表格字段、按钮顺序、分页排序、行内操作是否一致。
3. 弹窗、抽屉、独立页面等容器是否被正确还原。
4. 页面级AI Coding指导中的开发项、复用对象和差异内容是否落实。
5. 空状态、加载态、异常态、无权限态、极端情况和Mock数据覆盖是否完整。
6. 是否遗漏HTML说明书中的关键字段、操作、状态或联动规则。

### 4.4 HTML与Coding的关系

- 交互逻辑补齐规则用于生成HTML设计说明书中的页面交互、状态、边界和基础表现。
- 编码指导规则用于生成HTML设计说明书中的总览级与页面级AI Coding指导、Mock数据要求和Coding计划。
- HTML设计说明书是需求到Coding之间的可审阅中间产物和实现边界说明，不是机械执行稿。
- 当HTML与用户确认内容、业务设计Skill或已有代码冲突时，按更高优先级依据修正实现。
