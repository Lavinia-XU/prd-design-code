## 1. 概览

Coding指导规范用于把页面设计说明转化为AI编程工具可执行的前端Demo实现要求。Demo重点是让用户直观看到需求对应的页面、流程、交互和基础逻辑限制，不需要实现真实后端接口、数据库、鉴权或复杂算法，除非用户明确要求。

## 2. 交互逻辑规则

### 2.1 关键交互说明来源与补齐原则

页面关键交互说明必须从五类信息中综合生成：

1. 需求资料：用户明确提到的操作、流程、状态、限制、字段、按钮和业务结果。
2. 业务设计Skill：产品介绍、页面导航结构、页面说明、页面设计规范、同类功能交互、弹窗/抽屉习惯和菜单命名。
3. Demo代码环境：已有路由、菜单配置、相似页面、组件组织、Mock数据结构、状态管理和交互处理方式。
4. 通用设计库：仅在业务设计Skill未覆盖、未说清楚或用户未提供业务设计Skill时使用；先按需求命中的主题读取主题类设计文档作为框架级参考，再结合实际业务对字段配置、字段展示、操作和状态进行增删减；主题类设计未覆盖时，再用基础设计库中的页面类型、表格、表单、详情、Tab、二次确认、长表单、轻量配置入口和多层级下钻设计手法补充。
5. AI业务理解：基于业务目标、用户任务、页面容器类型和Demo可演示性进行合理补齐。

AI补齐可用于修正需求中缺失但从产品专业性、行业通用设计和用户体验友好程度看需要完善的内容，例如基础交互、前端状态、Demo逻辑限制、Mock数据覆盖、校验提示、空状态和异常反馈。补齐目标仅限于确保产品达到可用、易用和可演示，不得偏离需求设定范围做过多发挥，不得新增复杂业务能力。

每个关键交互至少说明：

| 说明项 | 写法要求 |
| ------ | -------- |
| 触发入口 | 用户从哪个页面、区块、按钮、字段、统计数字或链接触发 |
| 触发方式 | 点击、输入后查询、选择筛选项、勾选后批量操作、切换Tab等 |
| 打开容器 | 跳转页面、打开抽屉、打开弹窗、展示Popover/Tooltip、Toast提示等 |
| 页面反馈 | 当前页面如何变化，如表格刷新、按钮loading、区块展开、状态标签变化 |
| 数据变化 | Mock数据如何更新，如新增一行、修改当前行、状态变为已处置、列表移除 |
| 校验规则 | 必填、格式、范围、依赖关系、批量选择为空、未保存离开等 |
| 成功反馈 | 成功文案、关闭容器、刷新范围、返回位置 |
| 失败反馈 | 错误提示、保留输入、允许重试 |
| 状态联动 | 列表、统计卡片、详情状态、Tab数量是否同步变化 |
| 边界状态 | 空状态、搜索无结果、加载态、异常态、无权限态、长文本等 |

禁止只写“点击查看详情”“点击提交”“点击删除”这类结果不完整的描述。

### 2.2 搜索、筛选、重置

| 交互 | 必须说明 | Demo实现要求 |
| ---- | -------- | ------------ |
| 搜索 | 搜索字段、匹配方式、触发方式 | 基于Mock数据做模糊匹配或精确匹配 |
| 筛选 | 筛选项、选项范围、是否可组合 | 多个筛选条件应组合生效 |
| 重置 | 重置哪些条件 | 清空筛选项并恢复默认列表 |
| 排序 | 默认排序字段、可排序字段 | 至少体现默认排序；可排序字段需要可点击切换升降序 |
| 分页 | 每页数量、总数展示 | 数据量超过一页时展示分页 |

### 2.3 新增、编辑、查看

- 新增和编辑默认复用同一表单容器，除非字段或流程明显不同。
- 查看如果只是同一组信息的只读态，可复用表单只读状态；如果包含状态、关联策略、运行记录、告警统计等额外信息，应拆为抽屉详情页或下钻详情页。
- 表单提交前必须校验必填项、格式、取值范围和依赖关系。
- 提交成功后需要说明反馈方式：关闭弹窗/抽屉、刷新列表、更新当前行状态、Toast提示等。
- 提交失败时保留用户已填写内容，并展示错误提示。

### 2.4 删除、禁用、处置、批量操作

高影响操作必须说明二次确认：

| 操作 | 二次确认 | 常见文案 | Demo反馈 |
| ---- | -------- | -------- | -------- |
| 删除 | 必须 | 删除后数据不可恢复，确认删除？ | 删除成功后从列表移除或状态变更 |
| 禁用 | 必须 | 禁用后相关业务可能受影响，确认禁用？ | 状态变为已禁用 |
| 重启 | 必须 | 重启期间服务可能短暂不可用，确认重启？ | 展示操作中，再恢复状态 |
| 业务下线 | 必须 | 下线后业务访问可能受到影响，确认下线？ | 状态变为已下线或下线中 |
| 批量处置 | 必须 | 将对选中对象执行批量操作，确认继续？ | 批量更新状态或提示部分成功 |
| 未保存离开 | 必须 | 当前修改未保存，离开后不会生效，是否保存？ | 保存、放弃、继续编辑 |

高危操作可增加管理员密码、输入对象名称或二次勾选确认，但仅在业务确有风险时使用。

## 3. 代码环境结合规则

当存在Demo代码环境、用户指定代码范围、业务设计Skill提到参考模块或用户提到已有模块时，AI Coding指导必须结合代码结构生成。

重点读取并转化为Coding指导的内容：

- 路由和菜单配置：用于判断页面入口、导航路径和是否新增菜单或Tab。
- 相似页面实现：用于复用页面布局、表格工具栏、筛选表单、详情容器、弹窗和抽屉模式。
- 组件组织方式：用于说明应复用的组件、样式和交互反馈方式。
- Mock数据和状态结构：用于定义Demo数据字段、状态值、列表更新和筛选逻辑。
- 现有交互处理：用于沿用搜索、重置、分页、二次确认、Toast、loading和异常提示习惯。

如果代码与需求、业务设计Skill或通用设计库存在冲突，必须进入待确认问题，并在AI Coding提示词中标记当前默认假设。不要把后端接口、数据库、任务调度等技术实现写成Demo页面功能。

## 4. 待确认问题使用规则

在输出AI Coding指导摘要前，先生成待确认问题。待确认问题用于约束AI Coding的默认假设，避免在导航结构、用户旅程或关键业务规则不明确时误写成事实。

待确认问题只保留会影响以下内容的问题：

- 导航结构：新增菜单、复用已有菜单、Tab归属、菜单层级和命名冲突。
- 页面容器：页面、抽屉、弹窗、详情页、配置页的选择。
- 用户旅程闭环：入口、任务完成后的返回位置、审批/提交/处置流转、旅程卡点。
- 关键业务规则：状态流转、权限、二次确认、高危校验、处置原因、批量操作。
- Coding实现：复用组件、Mock数据状态、与已有页面联动、是否读取指定模块。
- 关键需求缺失：入口、目标用户、核心操作结果、状态定义、关键字段或列表对象。

数量最多10个，优先3-6个。每个问题必须写影响范围和当前默认假设。若问题不阻断Demo闭环，按默认假设继续生成HTML和Coding提示词；若问题阻断Demo成立，在对话框中优先提示用户确认。

## 5. 状态与边界规则

### 3.1 基础状态

| 状态 | 出现场景 | 页面表现 | 操作建议 |
| ---- | -------- | -------- | -------- |
| 空状态 | 初始无数据 | 展示空状态文案和图标 | 提供新增或刷新入口 |
| 搜索无结果 | 查询条件无匹配 | 展示“暂无符合条件的数据” | 提供重置筛选 |
| 加载态 | 查询、筛选、切换页面 | 表格或内容区展示loading | 禁用重复点击 |
| 提交中 | 表单提交、批量操作 | 按钮loading | 防止重复提交 |
| 提交失败 | 网络异常或校验失败 | Toast或表单错误提示 | 保留已填写内容 |
| 无权限态 | 用户无操作权限 | 按钮置灰或隐藏 | 悬浮提示无权限原因 |

### 3.2 极端情况

| 极端情况 | Demo体现方式 |
| -------- | ------------ |
| 长文本 | 单行省略，悬浮展示完整内容 |
| 数值为0 | 指标卡展示0，不隐藏卡片 |
| 字段为空 | 使用“-”或“暂无”展示，不留空白 |
| 数据量大 | 表格分页，每页10条或20条 |
| 状态很多 | 使用标签、筛选和排序帮助识别重点 |
| 高风险数据很多 | 默认按风险等级和发现时间排序 |
| 批量选择为空 | 点击批量操作时提示“请先选择数据” |
| 部分成功 | 批量操作后展示成功数和失败数 |

## 6. Mock数据规则

Mock数据必须服务于Demo展示和逻辑验证，不只是填满表格。

### 4.1 列表数据

列表类页面至少提供10-15条Mock数据，覆盖：

- 主要状态：如正常、告警、离线、待处置、处理中、已处置。
- 主要类型：如高/中/低风险，启用/禁用，成功/失败。
- 至少1条长文本，用于验证省略和悬浮提示。
- 至少1条字段为空，用于验证空值展示。
- 至少1条高优先级或异常数据，用于默认重点展示。
- 如果有时间筛选，Mock数据应覆盖不同日期。

### 4.2 表单数据

表单类Demo需要提供：

- 默认值。
- 下拉选项、单选项、复选项。
- 必填校验示例。
- 格式错误示例。
- 字段联动示例。
- 高级配置默认收起或展开规则。

### 4.3 详情数据

详情类Demo需要提供：

- 对象信息卡片数据。
- 描述列表字段。
- 关联表格数据。
- 时间线或操作记录。
- 状态、风险、处置建议等用于帮助用户判断的信息。

## 7. 组件与样式建议

默认组件建议：

- 概览指标：卡片、数字、趋势或状态标签。
- 查询条件：筛选表单、输入框、下拉框、日期范围、重置按钮。
- 主数据：表格、分页、排序、行内操作。
- 中等复杂详情：抽屉详情页。
- 轻量表单：弹窗表单页。
- 中等复杂表单：抽屉表单页。
- 高危确认：弹窗二次确认。
- 状态表达：Tag、状态点、图标+文字。
- 长文本：Tooltip。
- 操作反馈：Message、Toast、Alert。

如果用户指定Ant Design等组件库，优先映射到对应组件：Table、Form、Card、Drawer、Modal、Tag、Tooltip、Message、Alert、Tabs、Steps、Pagination。

## 8. AI Coding提示词要求

提示词必须包含：

1. 需求名称和体验目标。
2. 页面实现清单。
3. 页面结构和逐页设计说明引用。
4. 交互规则：搜索、筛选、重置、排序、分页、查看、新增、编辑、删除、处置、二次确认。
5. 状态规则：空状态、搜索无结果、加载态、提交中、提交失败、无权限态、极端情况。
6. Mock数据要求。
7. 当前默认假设；未确认内容不能写成已确认事实，待确认问题只在对话框展示，不写入HTML。
8. 如果读取了现有代码，说明参考的模块、建议复用的组件模式和需要保持一致的交互习惯。
9. 不需要实现的内容：真实后端接口、数据库、鉴权、复杂算法、外部系统联调。
10. 输出形式：可运行Demo页面或在现有项目中完成对应页面。
11. 目录开发要求：左侧目录用于切换页面内容，不要使用URL hash定位锚点开发目录。

Coding指导放置规则：总结性实现建议、全局Mock数据要求和完整AI Coding提示词放在HTML总览页；针对单个页面的组件、Mock数据、状态更新和代码复用建议放在对应页面内。若页面内容区简要引用了业务设计Skill或通用功能点设计，页面级Coding建议必须增加关联说明，说明命中的功能点设计、使用位置、实现方式、建议复用的组件或代码、需要覆盖的Mock数据和边界状态。

## 9. Coding计划执行规则

HTML设计说明书生成后，先提醒用户查看HTML页面内容；如果HTML中有需要调整的页面结构、字段、交互、状态或说明内容，用户可以直接告知修改点。随后输出具体Coding计划并询问用户是否确认执行；只有用户明确同意后才开始开发。Coding计划只确认开发实现方式，不重新确认业务设计内容；业务设计相关问题应在第四步待确认问题中完成确认。若用户在确认Coding前提出HTML修改意见，先更新设计说明JSON并重新生成最新HTML，再重新输出Coding计划确认，不得基于旧HTML直接开始开发。

HTML设计说明书是需求到Coding之间的可审阅中间产物和实现边界说明，用于对齐页面范围、页面结构和显性设计决策；它不是Coding唯一输入，也不是机械执行稿。Coding时必须结合原始需求、用户确认内容、业务设计Skill、通用设计库、功能点设计、已有代码和HTML设计说明书综合判断。

页面开发必须回到页面类型对应的基础设计规则做还原检查。页面类型不是标签，开发时必须转化为具体布局、区块顺序、组件组合和交互逻辑。

### 9.1 Coding输入来源与HTML使用原则

执行Coding时，必须综合以下输入：

1. 用户原始需求、PRD或Demo范围：用于理解真实业务目标、用户意图、关键字段、操作和约束，防止HTML压缩后丢失上下文。
2. 用户在待确认问题中的回复：优先级高；如果用户回复改变导航、页面结构、功能范围或实现方式，必须覆盖HTML草案并同步更新HTML。
3. 业务设计Skill：用于保持产品导航、页面规范、组件模式、筛选方式、固有字段和交互习惯一致。
4. 通用设计库、主题设计和功能点设计：用于补充页面类型、交互、状态、边界和局部功能点细节。
5. 已有代码环境：用于确认真实可复用的路由、菜单、组件、Mock数据、状态管理、UI库和样式模式。
6. HTML设计说明书：用于确认页面范围、页面目录、页面区块、关键交互、页面级Coding建议和显性设计决策。

HTML中的页面目录、页面总览、页面类型、页面布局、页面容器、主入口、区块和显性设计决策是Coding的重要约束；但当HTML与用户确认内容、业务设计Skill或已有代码冲突时，不得机械照搬HTML，应按更高优先级依据修正实现，并在Coding计划或页面完成反馈中简要说明修正原因。仍不确定且会影响页面结构、导航或核心旅程时，暂停并向用户说明影响。

### 9.2 HTML查看与修改处理

- 在输出Coding计划前，必须提醒用户先查看HTML页面内容。
- 提醒用户如果HTML里有需要调整的页面结构、字段、交互、状态、文案或说明内容，可以直接告知修改点。
- 如果用户反馈HTML需要修改，先更新设计说明JSON并重新生成最新HTML，再基于最新HTML重新输出Coding计划确认。
- 用户确认开始Coding后，若再发现HTML说明书需要同步调整，应在执行代码修改的同时更新设计说明JSON并重新生成最新HTML，确保HTML与最终Demo实现一致。
- 不得在HTML存在已知修改意见时基于旧HTML开始开发。

### 9.3 Coding计划确认内容

Coding计划必须在开始开发前让用户确认以下内容，避免开发实现与用户预期不一致：

- 导航结构：明确本次开发页面的导航路径，包括一级菜单、二级菜单、三级菜单、Tab或页面入口；说明是新增路由、新增菜单，还是复用已有菜单或页面容器。
- 全新开发页面：列出本次AI全新开发的页面ID、页面名称、页面类型和容器形式。
- 参考已有页面开发：列出会参考哪个已经开发的页面、代码模块或目录，并说明参考的是布局、表格结构、表单容器、路由配置、样式还是交互逻辑。
- 复用已有功能点：列出页面内会复用的已有代码模块、组件、样式、Mock数据、状态管理或交互逻辑，不重新开发的范围必须写清楚。
- 新增实现功能点：列出本次需要新增编码实现的页面、交互、状态、Mock数据或前端逻辑。
- 开发顺序：按页面层级列出执行顺序，先父级主页面，再新增、编辑、详情、弹窗或抽屉等子页面。

不要在Coding计划中重新确认字段含义、业务规则、页面是否应该存在等业务设计问题；这些内容应在第四步待确认问题中完成确认。

### 9.4 页面级执行顺序

- 按HTML左侧页面目录和页面层级拆分Coding任务。
- 先开发父级主页面，再开发由主页面打开的新增、编辑、详情、弹窗或抽屉等子页面。
- 一个页面完成并自检后，再开始下一个页面。
- 不要一次性跨多个页面无序修改，避免入口、状态联动和Mock数据不一致。

### 9.5 页面开发前检查

每开发一个页面前，必须先确认：

1. 当前页面ID和页面名称。
2. 当前页面类型，并读取 [页面类型与页面元素说明](../04-design-basics/01-page-types.md) 中该页面类型的页面结构、页面元素说明、默认布局、区块顺序和组件组合。
3. HTML说明书中写明的页面类型还原要求，以及Wireframe / ASCII线框图是否继承了对应页面类型结构。
4. 业务设计Skill是否覆盖该页面的页面类型、筛选方式、组件实现或交互习惯。
5. 是否有相似代码、已有页面、已有组件或Mock结构可复用。
6. 是否有关联功能点设计，以及该功能点是融入页面区块、页面级Coding建议，还是拆为子页面/弹窗/抽屉。
7. 当前页面必须还原的页面区块列表、字段展示形式、按钮顺序、状态和边界。
8. 当前页面是否存在`基于页面目标闭环补齐`的内容；如果存在，Coding时需要实现这些补齐内容，并在用户否定补齐项时同步删除对应代码。

### 9.6 页面开发后还原检查

每开发完一个页面后，必须先做还原检查，再进入下一个页面：

1. 页面结构是否符合 [页面类型与页面元素说明](../04-design-basics/01-page-types.md) 中该页面类型定义的页面结构，不得只把页面类型当作标题标签。
2. 区块顺序是否与HTML设计说明书、Wireframe / ASCII线框图和页面类型文档一致。
3. 筛选搜索方式是否与业务设计Skill或HTML说明书一致。
4. 表格字段、展示形式、按钮顺序、分页排序和行内操作是否一致。
5. 弹窗、抽屉、独立页面等容器形态是否一致，不得把抽屉/弹窗做成页面内普通卡片。
6. 页面内容区引用的功能点是否按页面说明和页面级Coding建议实现。
7. 空状态、加载态、异常态、无权限态和极端情况是否实现。
8. Mock数据是否覆盖HTML说明书要求的关键状态和边界。
9. 是否遗漏HTML说明书中的关键字段、操作、状态或联动规则。
10. 完成以上检查后，才能进入下一个页面开发。

### 9.7 每页完成反馈

每完成一个页面，必须简要告知用户：

```text
已完成 <页面ID-页面名称> 的开发，包含：<关键界面、主要交互、状态或Mock数据>。
接下来开发 <页面ID-页面名称>。
```

如果当前页面是最后一个页面，改为：

```text
已完成 <页面ID-页面名称> 的开发，全部页面已开发完成。
```

### 9.8 全部完成反馈

所有页面开发完成后，必须告知：

```text
Demo已开发完毕，请告知有哪些需要调整的。你可以从页面结构、字段内容、交互逻辑、状态展示、样式细节或Coding效果上提出修改。
```
