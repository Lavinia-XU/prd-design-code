## 1. 概览

Demo设计规格用于把需求转化为可查看、可实现、可指导AI Coding的页面设计说明。HTML说明书是需求到Coding之间的可审阅中间产物，用于给用户确认页面范围、页面结构和显性设计决策，也用于在Coding效果不好时回溯问题来源；它不是Coding唯一输入，也不是机械执行稿。对话框只展示到页面总览表；页面总览之后的逐页设计说明、交互逻辑、状态规则、Mock数据和AI Coding提示词必须进入HTML说明书。

页面类型定义为：能独立承载一个业务目标的容器，不限于狭义页面，也包括弹窗和抽屉。

## 2. 输出边界

### 2.1 对话框只输出到页面总览

对话框允许输出：

- 需求与Demo范围
- 核心用户与场景
- 导航结构
- 页面总览表
- HTML文件路径和简短说明

### 2.2 HTML承载详细内容

以下内容必须写入HTML，不在对话框展开：

- 逐页设计说明
- 页面内容区块细节
- 可点击操作、搜索筛选、状态值、表单选项和校验说明
- 搜索筛选、重置、排序、分页规则在对应区块中的说明
- 新增、编辑、查看、删除、处置、启用、禁用等操作在对应区块或底部操作中的说明
- 二次确认、表单校验、状态反馈、极端情况在对应区块中的说明
- Mock数据要求
- AI Coding完整提示词

## 3. Demo范围过滤

需求文档可能包含商业选型、用户Playbook、技术方案、线下交付流程或外部系统操作。输出页面设计前，必须先判断哪些内容属于当前平台Demo可展示和可操作的范围。

| 类型 | 含义 | 是否进入Demo设计 |
| --- | ---- | --------------- |
| 平台内操作 | 用户在当前产品控制台中完成配置、创建、编辑、审批、提交、启用、禁用、查询、处理等操作 | 是 |
| 平台内展示 | 当前平台展示状态、结果、数据、日志、告警、风险、进度、详情等 | 是 |
| 线下流程 | 商务沟通、客户调研、POC、售前评估、线下实施、人工交付、运营跟进等 | 否，仅作为背景或待确认 |
| 外部系统/其他平台 | 在客户系统、第三方系统、内部运营平台、工单系统、云厂商后台等完成的操作 | 否，除非当前平台需要提供入口或展示结果 |
| 技术实现 | 技术架构、网络拓扑、接口设计、数据同步、部署脚本、算法逻辑、后台任务等 | 否，仅作为理解字段、状态或数据来源的依据 |
| 商业/运营背景 | 套餐、报价、商业选型、运营方案、客户分层、服务策略等 | 否，仅作为需求背景 |

过滤原则：只将平台内操作和平台内展示进入Demo页面设计；外部系统或线下流程不直接拆页面；技术实现不拆页面；大需求必须先过滤再拆页面。

## 4. 页面拆解逻辑

### 4.1 设计依据决策链路

设计依据不是普通参考资料，而是页面设计和AI Coding必须遵循的决策链路。页面类型、页面容器、页面区块、组件组合和交互细节必须沿着以下链路逐层确认，避免Coding阶段只把页面类型当作标签而没有还原对应结构。

#### 4.1.1 读取顺序

1. 需求资料：优先提取明确写出的页面、菜单、字段、操作、流程、状态、限制、用户任务和业务规则，用于确定本次要解决的问题、平台内操作范围、页面目标和关键字段。
2. Demo代码环境：如果当前存在代码仓库、用户指定代码范围、业务设计Skill提到参考模块，或用户提到已有模块，必须读取相关代码，用于校准已有路由、菜单、页面容器、组件实现、筛选方式、状态展示、Mock数据和交互习惯。
3. 业务设计Skill：页面拆解和导航结构设计后，如果存在业务设计Skill，必须优先查阅其中的产品介绍、页面导航结构、页面说明、页面设计规范和同类模块设计规则，校准菜单层级、命名、页面归属、页面类型、容器选择、字段表达、筛选搜索方式和弹窗/抽屉等交互方式；如果业务设计Skill明确规定页面结构、筛选方式或组件方式，优先遵循业务设计Skill。
4. 主题类设计库：只有业务设计Skill没有覆盖、没有说清楚，或用户没有提供业务设计Skill时，才按需求命中的主题查阅 [02-theme-patterns](../02-theme-patterns/) 中的主题类设计文档；主题类设计用于确定该业务主题的常见页面组合、页面关系和主流程框架，只作为框架参考，必须结合实际业务对页面数量、字段配置、字段展示、操作和状态进行增删减调整。
5. 功能点设计库：主题类设计没有覆盖或仍未说清楚时，按需读取 [03-function-patterns](../03-function-patterns/) 中的功能点设计文档；功能点设计用于补充局部功能点的交互细节，不得破坏页面类型定义的主结构。轻量功能点融入页面区块说明，中等功能点在页面内容区简述并在页面级Coding建议中给出关联说明，复杂功能点拆为子页面、弹窗或抽屉。
6. 基础设计库：功能点设计仍未覆盖时，按需读取 [01-page-types.md](../04-design-basics/01-page-types.md)、[02-table-patterns.md](../04-design-basics/02-table-patterns.md)、[03-form-patterns.md](../04-design-basics/03-form-patterns.md)、[04-layout-patterns.md](../04-design-basics/04-layout-patterns.md)、[05-interaction-patterns.md](../04-design-basics/05-interaction-patterns.md)、[06-state-patterns.md](../04-design-basics/06-state-patterns.md)，用于确定页面类型对应的基础布局、区块顺序、组件组合、交互边界和状态边界。页面类型一旦确定，必须继承基础设计库中该页面类型的默认结构。
7. AI业务理解：仅用于补足Demo可演示和Coding所需的缺失细节，不得覆盖前面已经明确的依据，不得引入无需求依据的复杂业务能力。

#### 4.1.2 每类依据负责什么

| 依据 | 决定什么 | 不决定什么 |
| ---- | -------- | ---------- |
| 需求资料 | 用户目标、业务规则、字段、操作范围、平台内可展示和可操作内容 | 不直接决定最终页面布局和组件实现 |
| Demo代码环境 | 路由习惯、菜单配置、组件实现方式、Mock结构、交互习惯、样式模式 | 不新增需求中没有的业务能力 |
| 业务设计Skill | 产品导航、页面规范、页面类型、页面容器、组件习惯、筛选方式、产品固有字段、字段配置方式和字段展示形式 | 不覆盖用户明确提出的新需求 |
| 主题类设计库 | 页面组合、页面关系、主流程框架、该主题常见的固有字段、配置方式和展示形式 | 不作为字段、操作和状态的全文照搬，需结合实际业务增删减 |
| 功能点设计库 | 局部功能点交互和实现细节 | 不改变页面主结构和页面类型约束 |
| 基础设计库 | 页面类型、布局、区块顺序、基础组件规则 | 不决定具体业务字段和业务状态 |
| AI业务理解 | 修正需求中缺失但从产品专业性、行业通用设计和用户体验友好程度看需要完善的基础内容，如缺失状态、边界、Mock数据、校验提示和可演示细节 | 不覆盖明确依据，不偏离需求设定范围做过多发挥，不新增复杂业务能力 |

#### 4.1.3 页面类型强制继承规则

页面类型不是页面标题旁的标签，而是页面结构硬约束。一旦页面类型确定，HTML设计说明书和Coding实现必须继承对应页面类型的默认布局、区块顺序和组件组合；只有业务设计Skill或用户明确要求覆盖时，才允许调整。

| 页面类型 | Coding必须还原的结构 |
| -------- | -------------------- |
| 基础表格页 | 搜索/筛选、表格工具栏、表格、分页、行内操作 |
| 概览表格页 | 顶部概览指标、下方搜索/筛选、表格、分页、行内操作 |
| 左树表格页 | 左侧树结构、右侧搜索/筛选、表格、分页、行内操作 |
| 概览左树表格页 | 顶部概览指标、下方左树右表、筛选、分页、行内操作 |
| 配置表单页 | 字段分组、必填校验、默认值、底部操作、未保存离开提醒 |
| 弹窗表单页 | 弹窗容器、轻量表单、确认/取消、提交校验和反馈 |
| 抽屉表单页 | 抽屉容器、表单字段、底部按钮、提交/取消和状态反馈 |
| 弹窗列表页 | 弹窗容器、搜索/筛选、列表或表格、选择/确认/取消 |
| 抽屉列表页 | 抽屉容器、对象上下文、关联列表、搜索/筛选、分页 |
| 抽屉详情页 | 抽屉容器、对象摘要、描述列表/表格、操作入口和关闭入口 |
| 下钻详情页 | 独立详情页、对象信息卡、多区块或Tab、返回入口和相关操作 |

HTML逐页说明中建议在页面基础信息或页面级Coding建议中写明“页面类型还原要求”，帮助Coding阶段按页面类型还原。

#### 4.1.4 冲突处理规则

当多个依据冲突时，按以下规则处理：

1. 用户明确要求 > 业务设计Skill > Demo代码环境 > 主题类设计库 > 功能点设计库 > 基础设计库 > AI业务理解。
2. 页面主结构冲突时，以业务设计Skill和页面类型强制继承规则为准。
3. 局部功能点冲突时，以业务设计Skill或功能点设计为准，但不得破坏页面主结构。
4. 组件实现冲突时，以Demo代码环境和业务设计Skill为准。
5. 筛选搜索方式冲突时，以业务设计Skill明确说明为准；业务设计Skill未说明时，再参考代码环境、主题类设计和基础设计规则。
6. 若冲突会影响导航、页面总览、页面容器、核心旅程或Coding实现，必须进入待确认问题。

### 4.2 需求颗粒度不足时的专业补齐规则

当需求资料只描述功能目标、业务效果或流程，没有提供页面级字段、筛选项、操作按钮、表单项时，不要停止输出，也不要把所有缺口都转为待确认问题。AI应先根据业务设计Skill、通用设计库、主题模板和常见B端产品模式，补齐可保证用户旅程闭环的页面设计。

补齐优先级如下：

1. 用户旅程闭环：确保用户从进入页面、查看数据、筛选定位、进入详情、完成配置、提交保存、查看结果都有连续路径。
2. 功能点闭环：每个功能点必须能独立完成，例如分析类功能不能只有列表无详情，配置类功能不能缺少保存/取消/默认值/校验反馈。
3. 数据闭环：列表字段、详情字段、表单字段、状态字段、操作结果之间要能互相解释，避免列表展示了数字但无法查看明细。
4. 操作闭环：必填下拉、单选、多选、时间范围等控件必须提供默认值、选项来源或兜底选项，避免用户无法完成操作。
5. 状态闭环：加载、空数据、无权限、禁用、失败、成功、处理中等关键状态需要补齐，避免交互断点。
6. 页面层级闭环：如果列表页无法承载完整任务，应补充详情页、抽屉、弹窗或结果页。

对补齐内容无需逐项询问用户，应在设计说明中体现为合理默认设计。待确认问题只保留影响方向和边界的大问题，例如业务范围、用户角色、权限边界、关键流程、合规要求、真实接口、真实字段或真实数据模型。不要把字段命名、按钮文案、普通筛选项、常规表格字段等可由AI合理补齐的内容全部列为待确认问题。Demo完成后，允许用户基于HTML页面再反馈字段、布局和文案细节，AI再更新设计说明与HTML。

反例：告警事件分析只有事件列表页，没有事件详情页，导致用户无法完成分析任务；配置表单中必填下拉没有默认选项或选项来源，导致用户无法提交配置；表格中展示“关联规则组数量”，但点击后无法查看具体规则组，导致信息链路断开。

正确做法：分析类页面需要补充详情页、详情抽屉或分析面板；配置类页面需要补齐默认值、选项来源、校验反馈和保存结果；列表中的聚合数字、对象数量、命中次数等可点击信息，需要补充明细查看方式。

### 4.3 业务设计Skill识别方式

业务设计Skill统一指包含业务基础产品介绍、页面导航结构、页面设计规范和相关页面说明的Skill，不再区分业务知识库Skill。

识别时先通过Skill名称和描述判断：

- 名称中包含深信服产品英文缩写 aTrust、ZTP、DSP、SASE、XDR、MSS、DR、aES。
- 或描述中同时包含具体深信服产品名称、设计、业务设计规范等关键词。
- 例如“为深信服下一代端点安全产品路由策略类产品设计与前端交付需求”可作为业务设计Skill使用。

### 4.4 关键交互说明生成依据

页面关键交互说明必须综合以下五类信息生成：

1. 需求资料：提取明确写出的用户操作、业务流程、状态限制、字段联动、审批/处置规则、异常限制和成功结果。
2. 业务设计Skill：如果识别到业务设计Skill，优先参考既有产品导航、页面说明、页面设计规范、弹窗/抽屉使用习惯、菜单命名和同类功能交互模式。
3. Demo代码环境：如果存在相关代码，读取已有路由、菜单配置、页面结构、组件组织、表单/表格/抽屉/弹窗实现、Mock数据结构和状态管理方式，校准交互落地方式。
4. 通用设计库：只有业务设计Skill未覆盖或未说清楚时，先按需求命中的主题查阅 [02-theme-patterns](../02-theme-patterns/) 中的主题类设计文档，获取框架级交互参考；主题类设计不代表必须完全照搬，需结合实际业务对字段、展示、操作和状态做增删减；如果主题类设计没有覆盖，再按需读取 [03-function-patterns](../03-function-patterns/) 中的功能点设计文档；如果功能点设计仍未覆盖，再按需读取 [01-page-types.md](../04-design-basics/01-page-types.md)、[02-table-patterns.md](../04-design-basics/02-table-patterns.md)、[03-form-patterns.md](../04-design-basics/03-form-patterns.md)、[04-layout-patterns.md](../04-design-basics/04-layout-patterns.md)、[05-interaction-patterns.md](../04-design-basics/05-interaction-patterns.md)、[06-state-patterns.md](../04-design-basics/06-state-patterns.md)，用B端常见页面类型、表单、表格、详情、Tab、二次确认、多层级下钻等基础设计手法补齐交互。
5. AI业务理解：当资料没有明确描述但Demo需要可操作、可演示、可Coding时，基于业务目标、用户任务和页面容器类型合理补齐基础交互，但不得引入无需求依据的复杂业务能力。

关键交互说明至少覆盖：触发入口、触发方式、打开容器、页面反馈、数据变化、表单校验、成功反馈、失败反馈、状态联动、空状态、加载态、无权限态和必要的极端情况。

### 4.5 拆解规则

- 独立路由、独立菜单入口或独立任务：按页面类型拆解，可拆为完整页面、弹窗表单页、弹窗列表页、抽屉表单页、抽屉列表页、抽屉详情页等。
- 二次确认、删除确认、禁用确认、小i说明、悬浮提示等轻量提示不拆页面，只在HTML交互规则中说明。
- 同个对象的新增、编辑、查看默认共用同一个页面、弹窗或抽屉；只有展示内容明显不同时，才拆为不同页面。
- 三级菜单下用于承载独立业务层级的Tab菜单需要独立编号；页面内容中的普通Tab不单独编号。
- 表单、详情、弹窗、抽屉通常通过页面操作进入，不作为独立菜单入口。

## 5. 代码环境读取规则

### 5.1 触发读取条件

出现以下任一情况时，必须读取相关代码作为输入：

- 当前工作环境存在Demo代码仓库，且用户希望基于现有Demo继续设计或Coding。
- 用户明确指定代码范围、文件路径、页面模块或已有菜单。
- 业务设计Skill提到可参考的产品模块、页面或组件。
- 需求明显是在已有产品页面上新增、改造或组合能力。

### 5.2 重点读取内容

优先读取：路由配置、菜单配置、页面入口、相似模块页面、表格/表单/详情/弹窗/抽屉组件、Mock数据、状态枚举、交互处理、样式规范和组件库使用方式。

读取代码的目的不是分析后端实现，而是校准以下设计决策：

- 是否复用已有页面，还是新增菜单或Tab。
- 页面名称、菜单层级和导航路径是否与现有产品一致。
- 新增/编辑/查看应使用页面、抽屉还是弹窗。
- 搜索、筛选、表格、分页、状态标签、二次确认和Toast反馈是否沿用已有实现习惯。
- Mock数据结构、字段命名和前端状态更新方式是否与现有Demo兼容。

### 5.3 读取结果使用方式

- 代码读取结论只作为页面设计、交互说明和Coding指导的输入，不把接口、数据库、任务调度等后端技术细节写成页面功能。
- 如果代码与需求或业务设计Skill冲突，优先把冲突列入待确认问题，并写明当前默认假设。
- 如果代码范围不明确但可能影响设计，在待确认问题中提醒用户指定参考模块。

## 7. 待确认问题

### 7.1 生成时机

在生成HTML设计说明书和AI Coding指导之前，必须先生成待确认问题，并放在对话框的页面总览表之后。待确认问题用于帮助用户判断会影响Demo设计和Coding准确性的关键不确定项，不写入HTML说明书。输出待确认问题后必须等待用户确认，确认前禁止直接生成完整HTML和AI Coding指导。

### 7.2 筛选原则

只保留符合以下任一条件的问题：

- 影响导航结构：新增菜单、复用已有菜单、作为Tab、菜单层级变化或命名冲突。
- 影响页面容器：独立页面、抽屉、弹窗、详情页或配置页的选择。
- 影响用户旅程闭环：入口、完成任务后的返回位置、审批/提交/处置闭环、旅程卡点或断点。
- 影响关键业务规则：状态流转、权限、二次确认、高危校验、处置原因、批量操作规则。
- 影响Coding实现：是否复用已有组件、Mock数据是否覆盖特定状态、是否与已有页面联动。
- 关键需求缺失：缺少入口、目标用户、核心操作结果、状态定义、关键字段或列表对象。

### 7.3 数量与格式

- 最多10个，优先控制在3-6个。
- 不问颜色、按钮位置、普通文案等低价值问题。
- 不问已经能从需求、业务设计Skill或代码中明确判断的问题。
- 每个问题必须包含“影响范围”和“当前默认假设”。
- 输出待确认问题后停止，等待用户确认或修正；用户确认后，先判断确认结果是否影响导航结构、页面总览、页面层级、入口方式、容器选择、关键交互或Coding方式。
- 若确认结果影响第三步已输出内容，必须先重新输出更新后的导航结构和页面总览表，再按更新后的内容生成HTML说明书和AI Coding指导。
- 若没有关键待确认问题，写明“暂无关键待确认问题，按当前页面总览继续生成HTML说明书”，此时可继续生成HTML。

```markdown
| 序号 | 待确认问题 | 影响范围 | 当前默认假设 |
| ---- | ---------- | -------- | ------------ |
| 1 | <问题> | <导航结构/页面容器/用户旅程/业务规则/Coding实现> | <默认假设> |
```

## 9. HTML说明书结构

HTML说明书标题必须是“XX需求设计说明书”。左侧为目录，右侧为内容区。Coding实现目录时不要使用URL hash定位锚点；左侧目录只用于切换右侧页面内容，应通过组件状态、路由状态或数据驱动选中态实现。

左侧目录只包含：总览和页面目录。禁止在HTML目录中放待确认问题、独立的交互与逻辑规则页或独立的Coding指导页。

页面目录必须按页面层级结构展示，而不是扁平罗列；页面名称必须带页面ID，格式为`页面ID-页面名称`。例如：

## 10. 自检规则

- 对话框主体是否只输出到页面总览表，之后只给待确认问题、HTML文件路径和简短说明。
- Demo范围是否过滤掉线下流程、外部系统、技术实现和商业背景。
- 用户提到已有模块、参考模块或当前存在Demo代码环境时，是否读取相关代码作为页面拆解、交互说明和Coding指导输入。
- 待确认问题是否控制在10个以内，且每个问题包含影响范围和当前默认假设。
- 页面总览表中的页面ID、页面名称、页面类型和HTML逐页说明是否一致。
- HTML中每个页面是否包含页面区块、字段展示、按钮、可点击操作和点击结果。
- HTML中搜索、筛选、重置、分页、排序是否已整合到对应页面的表格区、工具栏或相关内容区块说明中。
- HTML中新增、编辑、删除、处置、启用、禁用等操作是否已整合到对应页面的区块说明或底部操作中，并写清校验、反馈和状态变化。
- HTML中高影响操作是否有二次确认。
- HTML中空状态、加载态、异常态、无权限态和极端数据是否覆盖。
- HTML中Mock数据是否覆盖主要状态和边界情况。
- HTML说明书是否包含标题、左侧目录、总览页和按页面层级组织的逐页内容；是否没有把待确认问题、全局交互规则页或独立Coding指导页放入HTML目录。
