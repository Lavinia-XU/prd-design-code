## 1. 概览

Demo设计规格用于把需求转化为可查看、可实现、可指导AI Coding的页面设计说明。HTML说明书是用户确认后的页面实现基线，也是Coding阶段必须遵循并逐项落实的实现契约：它用于给用户确认页面范围、页面结构和显性设计决策，也用于在Coding效果不好时回溯问题来源；Coding过程中如确需偏离说明书（如代码环境不支持、业务调整），必须显式记录差异并说明原因，不得静默偏离，也不得将说明书当作可选择性参考的前期材料。对话框只展示到页面总览表；页面总览之后的逐页设计说明、交互逻辑、状态规则、Mock数据和AI Coding提示词必须进入HTML说明书。

页面类型定义为：能独立承载一个业务目标的容器，不限于狭义页面，也包括弹窗和抽屉。

## 2. 输出边界

### 2.1 对话框只输出到页面总览

对话框允许输出：

- 需求与Demo范围
- 核心用户与场景
- 导航结构
- 页面总览表
- HTML文件路径和简短说明

### 2.2 HTML承载详细内容

以下内容必须写入HTML，不在对话框展开：

- 逐页设计说明
- 页面内容区块细节
- 可点击操作、搜索筛选、状态值、表单选项和校验说明
- 搜索筛选、重置、排序、分页规则在对应区块中的说明
- 新增、编辑、查看、删除、处置、启用、禁用等操作在对应区块或底部操作中的说明
- 二次确认、表单校验、状态反馈、极端情况在对应区块中的说明
- Mock数据要求
- AI Coding完整提示词

## 3. Demo范围过滤

需求文档可能包含商业选型、用户Playbook、技术方案、线下交付流程或外部系统操作。输出页面设计前，必须先判断哪些内容属于当前平台Demo可展示和可操作的范围。

| 类型 | 含义 | 是否进入Demo设计 |
| --- | ---- | --------------- |
| 平台内操作 | 用户在当前产品控制台中完成配置、创建、编辑、审批、提交、启用、禁用、查询、处理等操作 | 是 |
| 平台内展示 | 当前平台展示状态、结果、数据、日志、告警、风险、进度、详情等 | 是 |
| 线下流程 | 商务沟通、客户调研、POC、售前评估、线下实施、人工交付、运营跟进等 | 否，仅作为背景或待确认 |
| 外部系统/其他平台 | 在客户系统、第三方系统、内部运营平台、工单系统、云厂商后台等完成的操作 | 否，除非当前平台需要提供入口或展示结果 |
| 技术实现 | 技术架构、网络拓扑、接口设计、数据同步、部署脚本、算法逻辑、后台任务等 | 否，仅作为理解字段、状态或数据来源的依据 |
| 商业/运营背景 | 套餐、报价、商业选型、运营方案、客户分层、服务策略等 | 否，仅作为需求背景 |

过滤原则：只将平台内操作和平台内展示进入Demo页面设计；外部系统或线下流程不直接拆页面；技术实现不拆页面；大需求必须先过滤再拆页面。

## 4. 页面拆解逻辑

### 4.1 设计依据决策链路

设计依据不是普通参考资料，而是页面设计和AI Coding必须遵循的决策链路。页面类型、页面容器、页面区块、组件组合和交互细节必须沿着以下链路逐层确认，避免Coding阶段只把页面类型当作标签而没有还原对应结构。

#### 4.1.1 读取顺序

识别设计能力时，对照 [Design Skill Resolver - 能力识别参考框架](00-design-skill-resolver.md) 的五层（Theme 主题框架 / Template 页面模板 / Feature 业务功能 / Pattern 交互模式 / Component 组件映射）自查防漏：命中才读，未命中的层记录原因但不产生读取；禁止把五层当作全量读取清单。

1. 需求资料：优先提取明确写出的页面、菜单、字段、操作、流程、状态、限制、用户任务和业务规则，用于确定本次要解决的问题、平台内操作范围、页面目标和关键字段。
2. Demo代码环境：如果当前存在代码仓库、用户指定代码范围、Product Design提到参考模块，或用户提到已有模块，必须读取相关代码，用于校准已有路由、菜单、页面容器、组件实现、筛选方式、状态展示、Mock数据和交互习惯。
3. Product Design：页面拆解和导航结构设计后，如果存在Product Design，必须优先查阅其中的产品介绍、页面导航结构、页面说明、页面设计规范和同类模块设计规则，校准菜单层级、命名、页面归属、页面类型、容器选择、字段表达、筛选搜索方式和弹窗/抽屉等交互方式；如果Product Design明确规定页面结构、筛选方式或组件方式，优先遵循Product Design。
4. Common Design：如果存在Common Design，必须读取其中的页面类型模板、组件映射表和通用设计规则，用于确定页面骨架、组件选择、筛选方式和交互基线；Common Design是正式页面设计阶段的必需依赖，未查询到Common Design或查询到但无法成功读取其SKILL.md时，不得使用AI自身通用设计知识模拟，应停止进入正式页面设计并提示缺少Common Design。
5. AI业务理解：仅在用户资料、Product Design、Common Design和Demo代码环境未覆盖时，用于补足Demo可演示和Coding所需的基础细节；不得覆盖前面已经明确的依据，不得引入无需求依据的复杂业务能力。

#### 4.1.2 每类依据负责什么

| 依据 | 决定什么 | 不决定什么 |
| ---- | -------- | ---------- |
| 需求资料 | 用户目标、业务规则、字段、操作范围、平台内可展示和可操作内容 | 不直接决定最终页面布局和组件实现 |
| Demo代码环境 | 路由习惯、菜单配置、组件实现方式、Mock结构、交互习惯、样式模式 | 不新增需求中没有的业务能力 |
| Product Design | 产品导航、页面规范、页面类型、页面容器、组件习惯、筛选方式、产品固有字段、字段配置方式和字段展示形式 | 不覆盖用户明确提出的新需求 |
| Common Design | 页面类型模板、组件映射、页面骨架、筛选方式、按钮顺序和通用交互基线 | 不覆盖用户明确提出的新需求和Product Design明确的覆盖规则 |
| AI业务理解 | 修正需求中缺失但从产品专业性、行业通用设计和用户体验友好程度看需要完善的基础内容，如缺失状态、边界、Mock数据、校验提示和可演示细节 | 不覆盖明确依据，不偏离需求设定范围做过多发挥，不新增复杂业务能力 |


#### 4.1.3 页面类型决策表

进入页面总览前，必须为每个页面形成内部页面类型决策表。该表用于固定页面类型选择依据和后续继承关系，不要求在对话框完整展示；只有页面类型不确定且影响页面结构、用户旅程或导航时，才将问题进入待确认。

| 字段 | 要求 |
| ---- | ---- |
| 页面ID与业务场景 | 对应页面总览，说明用户要完成的任务和入口上下文 |
| PRD/用户约束 | 记录明确的容器、流程、字段、状态或操作约束 |
| Product Design覆盖 | 记录是否存在匹配规则及其`inherit / extend / override`关系；无匹配时明确为“未匹配，使用Common Design模式” |
| Common Design候选模板 | 仅列出已实际读取的标准页面类型模板 |
| 代码证据 | 记录已验证的相似页面、组件、路由或容器结构；无证据时明确标注 |
| 最终页面类型 | 使用 Common Design 标准页面类型中文名（如概览表格页、抽屉表单页），不得使用业务描述或模板 ID（如 page-table-overview）替代页面类型；若 Product Design 自定义了页面模板且声明覆盖（override），则以 Product Design 页面模板为准 |
| 决策理由 | 说明最终模板如何满足业务场景、PRD约束和已有实现 |
| 未决问题 | 仅记录会影响页面类型选择的不可推断事实 |

页面类型必须使用已读取Common Design、匹配Product Design或已验证代码中真实存在的页面模板名称。不得使用未在这些依据中出现的页面模板名称。若需求需要的页面结构无法匹配已有模板，统一标记为“自定义页面类型”，并说明继承的基础模板、扩展内容、结构差异及其来源。

#### 4.1.4 页面类型强制继承规则

页面类型不是页面标题旁的标签，而是页面结构硬约束。一旦页面类型确定，HTML设计说明书和Coding实现必须继承用户资料、Product Design或已有代码中明确的对应布局、区块顺序和组件组合；只有用户明确要求覆盖时，才允许调整。

每个页面类型对应的必需结构、区块顺序与组件组合一律以已读取的 Common Design 页面模板文档为准（若 Product Design 声明了页面模板覆盖，以 Product Design 为准），本 Skill 不保存各页面类型的结构清单，避免与 Common Design 不同步；读取页面模板文档时按 00-design-skill-resolver 的能力识别参考框架确认命中并读取对应模板条目。

HTML逐页说明中必须在页面基础信息里写明“页面类型还原要求”，并描述页面骨架组件。页面骨架组件信息从Common Design页面模板获取，只列标题栏、Tab、筛选区、工具栏、表格、分页、弹窗、抽屉、底部操作等骨架组件，不负责列出全部字段组件。

#### 4.1.5 HTML线框图绘制规则

如果HTML说明书中生成Wireframe / ASCII线框图，线框图必须继承用户资料、Product Design或已有代码中明确的当前页面类型结构，并从该页面类型对应的设计库模板文档读取模板结构与线框样式：匹配Product Design声明了页面模板时按Product Design定义的页面模板（按 00-design-skill-resolver 的覆盖关系），否则按Common Design页面模板文档（如 03-design-template/01-page-types.md 的对应模板条目）。页面类型不是线框图标题标签，而是线框图布局约束；本Skill不保存任何页面模板线框图参考，模板样式一律以运行时可读取的Common Design或匹配Product Design模板文档为准。

绘制线框图前，必须先确认用户资料、Product Design或已有代码中对应页面类型的页面结构和页面元素说明，并读取Common Design或匹配Product Design模板文档中该模板的布局样式。线框图必须严格按所选模板的布局结构绘制，只允许替换文案并完善内容区中的具体内容，禁止调整模板布局结构、区块顺序、容器形态或新增模板不存在的区域；不得仅根据页面名称、页面目标或AI经验自行组合线框图。

线框图绘制顺序：

1. 先根据页面类型继承基础页面结构，例如基础表格页、概览表格页、左树表格页、配置表单页、抽屉表单页、弹窗表单页、抽屉详情页或下钻详情页等。
2. 再按已确认的页面元素规则补充标题栏、工具栏、筛选区、表格、表单、底部操作、Tab、返回入口、关闭入口等通用部件。
3. 最后填入当前业务页面的字段、指标、按钮、状态、可点击操作和功能点入口。

页面内容区块、Wireframe / ASCII线框图和页面级Coding还原要求必须三者一致，并与页面类型决策表中的最终类型和模板依据一致。如果页面内容区块与已确认的页面类型结构冲突，优先修正页面内容区块；如果Product Design或已有代码明确覆盖页面结构，则以Product Design或已有代码为准，并在`wireframeNote`或页面类型还原要求中说明原因。

线框图绘制时禁止：

- 只画一个空白卡片或通用容器。
- 将抽屉或弹窗画成普通页面卡片。
- 将左树表格页画成普通表格页。
- 将概览表格页画成只有表格、没有概览区。
- 忽略已确认页面类型要求的标题栏、筛选区、工具栏、分页、底部按钮、关闭入口或返回入口。
- 将线框图画成"每行一个区域名：内容"的标签罗列样式（会被校验器以 RULE-34 阻断）。
- 在本Skill内自建或引用页面模板线框图样式；模板样式以运行时可读取的Common Design页面模板文档为准。
- 线框图内容与页面内容区块描述不一致。

生成HTML的JSON中，每个页面对象必须写入`wireframe`字段；如需解释容器关系、Tab层级、固定底部栏、页面类型继承关系或Product Design覆盖原因，写入`wireframeNote`字段。`wireframeNote`应说明线框图参考的页面类型和结构依据，例如“线框图按基础表格页绘制，包含筛选区、工具栏、表格和分页”。

#### 4.1.6 页面目标闭环检查

页面拆解和HTML说明生成前，必须检查每个页面是否形成目标闭环，避免只按需求字面翻译导致页面无法完成用户任务。对象管理类页面是否具备支撑对象生命周期的基础承载能力；流程/任务类页面是否具备开始、执行、结果和异常反馈；分析/事件类页面是否具备发现、查看详情和处理路径。若需求只描述局部操作，AI需要判断该操作依赖的上下文能力，并从Product Design、已有代码或AI业务理解中按需补齐。补齐内容必须标注为`基于页面目标闭环补齐`，且不能伪装成用户原始需求。会明显影响页面结构、业务规则或用户旅程的补齐项应进入待确认问题。补齐内容仅限于确保页面可用、易用、可演示，不得新增业务模块、复杂审批链路、跨系统联动或与需求目标无关的高级能力。

#### 4.1.7 冲突处理规则

当多个依据冲突时，按以下规则处理：

1. 用户明确要求 > Product Design > Common Design > Demo代码环境 > AI业务理解。
2. 页面主结构冲突时，以Product Design和页面类型强制继承规则为准。
3. 局部功能点冲突时，以Product Design或已有代码为准，但不得破坏页面主结构。
4. 组件实现冲突时，按具体实现优先级处理：用户或HTML明确要求复用的对象 > 当前代码环境中已验证的业务组件和页面框架 > Product Design推荐的具体实现 > Common Design推荐组件 > 通用iDux组件语义推断 > 全新开发；设计语义优先级（Product Design > Common Design > AI补齐）只决定设计知识来源，不决定实际复用对象。Demo代码环境中已有真实可用的同名业务组件时，必须优先于设计库推荐组件纳入复用判断。
5. 筛选搜索方式冲突时，以Product Design或Common Design页面模板明确说明为准；Product Design未说明时，再参考代码环境、主题类设计和基础设计规则。
6. 若冲突会影响导航、页面总览、页面容器、核心旅程或Coding实现，必须进入待确认问题。

### 4.2 页面目标闭环检查

页面拆解和HTML设计说明生成前，必须检查每个页面是否形成目标闭环。不要只做需求字面翻译；当需求只描述局部操作、功能目标、业务效果或流程时，AI需要判断该页面是否已经能支撑用户完成完整任务。

检查问题：

1. 页面目标闭环：用户进入页面后要完成什么任务，页面是否能支撑用户完成这个任务。
2. 对象生命周期闭环：如果页面承载一个业务对象，是否能支撑对象从查看、定位、创建、维护到结果确认的基础管理生命周期。
3. 流程闭环：如果页面承载一个流程，是否能支撑流程的开始、执行、结果和异常处理。
4. 分析闭环：如果页面承载分析场景，是否能支撑发现问题、查看详情和进一步处理。
5. 数据闭环：列表字段、详情字段、表单字段、状态字段、操作结果之间是否能互相解释，避免列表展示了数字但无法查看明细。
6. 状态闭环：加载、空数据、无权限、禁用、失败、成功、处理中等关键状态是否补齐，避免交互断点。

当页面目标不闭环时，应从用户需求上下文、Product Design、已有代码习惯和AI业务理解中补齐必要内容。补齐不是新增一套设计规则，也不是自由发挥，而是为了让页面目标完整、Demo可用、Coding可落地。

允许补齐：支撑页面目标完成的基础入口；支撑对象生命周期闭环的基础操作；支撑流程闭环的状态和结果；支撑Demo可演示的反馈、空状态、异常态和边界情况。

禁止补齐：新业务模块、新复杂流程、新审批链路、新跨系统联动、新角色权限体系，以及与需求目标无关的高级能力。

补齐内容应在页面总览、页面内容区块或页面级Coding建议中标注来源：`基于页面目标闭环补齐`。如果补齐内容会明显影响页面结构、业务规则、核心用户旅程或Coding实现，应进入待确认问题；如果只是字段命名、按钮文案、普通筛选项、常规状态反馈等可由AI合理补齐的内容，不要全部列为待确认问题。

反例：服务器管理只输出新增表单，没有列表承载和新增后的结果确认；告警事件分析只有事件列表页，没有事件详情页，导致用户无法完成分析任务；配置表单中必填下拉没有默认选项或选项来源，导致用户无法提交配置；表格中展示“关联规则组数量”，但点击后无法查看具体规则组，导致信息链路断开。

正确做法：对象管理类页面需要补齐支撑对象维护的基础承载能力；分析类页面需要补充详情页、详情抽屉或分析面板；配置类页面需要补齐默认值、选项来源、校验反馈和保存结果，并在生成HTML设计说明书前自检配置项是否为单列表单纵向排列、label与组件是否同一行、是否存在多列配置；列表中的聚合数字、对象数量、命中次数等可点击信息，需要补充明细查看方式。

### 4.3 Product Design识别方式

Product Design统一指包含业务基础产品介绍、页面导航结构、页面设计规范和相关页面说明的Skill，不再区分业务知识库Skill。

识别方式：

- 通过当前环境的Skill查询能力查找声明`skill_type: product-design`且需求产品名命中其任一产品标识的Skill；
- Product Design 通过 metadata 的 `product_id` 声明其服务的产品标识；同一产品存在多个名称（例如 AES 与 DR 为同一产品，需求资料中可能显示为 DR，但需使用 AES 的 Product Design）时，`product_id` 允许声明逗号分隔的多个标识（如 `product_id: aes, dr`），首个为主标识，其余为同一产品的别名标识；需求产品名（主名或别名）与任一标识一致（忽略大小写与空白）即判定匹配并可调用，不得要求需求产品名必须与主标识一致；
- 产品身份必须依据 Product Design 的 metadata、product_id（含同一产品的多标识声明）或 Design Skill Resolver 结果确定；禁止通过 Skill 名称中是否出现产品缩写（如 XDR、SASE、DSP 等）猜测，也禁止在通用 Skill 内容中硬编码具体产线或产品名称；
- 未找到匹配 Product Design 时，按 Common Design、当前代码环境和明确标记的AI补齐继续设计，不阻断流程。

### 4.4 关键交互说明生成依据

页面关键交互说明必须综合以下六类信息生成：

1. 需求资料：提取明确写出的用户操作、业务流程、状态限制、字段联动、审批/处置规则、异常限制和成功结果。
2. Product Design：如果识别到Product Design，优先参考既有产品导航、页面说明、页面设计规范、弹窗/抽屉使用习惯、菜单命名和同类功能交互模式。
3. Common Design：读取其中的页面类型模板、组件映射表和通用交互规则，用于确定交互基线、反馈方式和组件习惯；Common Design是正式页面设计阶段的必需依赖，未查询到Common Design或查询到但无法成功读取其SKILL.md时，不得使用AI自身通用设计知识模拟，应停止进入正式页面设计并提示缺少Common Design。
4. Demo代码环境：如果存在相关代码，读取已有路由、菜单配置、页面结构、组件组织、表单/表格/抽屉/弹窗实现、Mock数据结构和状态管理方式，校准交互落地方式。
5. AI业务理解：只有Product Design、Common Design和已有代码未覆盖时，基于B端常见页面类型、表单、表格、详情、Tab、二次确认、多层级下钻等设计手法补齐交互。
6. 补齐边界：当资料没有明确描述但Demo需要可操作、可演示、可Coding时，基于业务目标、用户任务和页面容器类型合理补齐基础交互，但不得引入无需求依据的复杂业务能力。

关键交互说明至少覆盖：触发入口、触发方式、打开容器、页面反馈、数据变化、表单校验、成功反馈、失败反馈、状态联动、空状态、加载态、无权限态和必要的极端情况。

### 4.5 功能入口承载判断

页面拆解时，先判断每个功能点的入口承载方式，再决定是否进入页面总览表。不要只根据功能名称看起来“可独立管理”就默认新增菜单、Tab或完整页面。

#### 4.5.1 优先作为独立菜单或菜单Tab的情况

满足以下任一条件时，优先考虑独立菜单、已有菜单下新增页面，或菜单Tab：

- 功能本身是用户高频进入的核心任务。
- 功能有独立业务目标和完整用户旅程，例如查看列表、筛选、详情、处置、配置、结果追踪。
- 功能需要稳定导航入口，用户需要反复进入。
- 功能包含较多对象管理能力，例如列表、新增、编辑、删除、批量操作、详情、状态流转。
- 功能需要承载多类子能力，弹窗或抽屉无法清晰表达。
- Product Design、已有代码或用户明确要求放入导航菜单或Tab。

#### 4.5.2 优先作为页面内按钮或工具入口的情况

满足以下多数条件时，不要默认拆成独立菜单或独立页面，优先放在相关对象或相关页面中，作为页面内按钮、工具栏按钮、行内操作或详情区操作入口：

- 功能属于非核心旅程中的辅助配置、全局配置或对象关联配置。
- 用户通常是在处理某个对象或某个主页面任务时才需要进入该功能。
- 功能不需要用户长期高频单独访问。
- 功能本身没有完整独立旅程，只是为了辅助主页面完成配置。
- 配置对象少、字段少、状态少，主要是新增、编辑、选择或关联。
- 功能与某个已有页面或对象强相关，例如在策略页配置标签、在线路页配置带宽保护、在资源页选择地址池。
- 如果单独放菜单，会让导航膨胀或割裂用户任务。

非核心配置的轻量入口适用于标签管理、带宽保护设置、全局地址池管理等辅助配置、全局配置或对象关联配置。这类能力通常不需要单独起菜单，优先将入口放在相关对象或相关页面中，通过页面内按钮或工具入口触发，并由弹窗、抽屉或必要的下钻页面承载。

#### 4.5.3 页面内入口的容器选择

当功能判断为页面内轻量入口后，按以下规则选择容器：

- 弹窗表单页：配置内容少、字段少、一次性完成、不需要保留复杂上下文。
- 抽屉表单页：配置内容中等复杂、需要保留当前页面上下文、需要展示对象摘要或配置分组。
- 弹窗列表页：需要临时选择对象，列表简单，选择后立即回到当前任务。
- 抽屉列表页：需要选择或查看较多对象，并且需要保留当前页面上下文。
- 下钻页面：配置内容复杂、字段多、需要多区块、多Tab、长时间编辑、稳定URL或独立保存流程。

#### 4.5.4 正反例

- 正例：在策略管理页中给策略绑定标签，不单独拆“标签管理”菜单，优先在策略表格工具栏或行内操作中提供“标签管理”或“设置标签”按钮，打开弹窗表单页或抽屉表单页。
- 正例：在线路配置页中设置带宽保护，如果只是给当前线路补充保护参数，优先作为线路详情或编辑页中的“带宽保护设置”按钮，打开抽屉表单页。
- 正例：在资源分配页中选择全局地址池，如果只是临时选择地址池对象，优先使用弹窗列表页或抽屉列表页，不单独拆地址池导航。
- 反例：标签本身有完整管理能力，包含标签列表、创建、编辑、删除、批量导入、权限控制和引用分析时，可以考虑独立菜单或Tab，而不是仅作为弹窗入口。
- 反例：地址池需要长期维护、被多个模块复用、存在容量监控、状态流转和批量操作时，应考虑独立配置页面或菜单Tab。

### 4.6 拆解规则

- 独立路由、独立菜单入口或独立任务：按页面类型拆解，可拆为完整页面、弹窗表单页、弹窗列表页、抽屉表单页、抽屉列表页、抽屉详情页等。
- 二次确认、删除确认、禁用确认、小i说明、悬浮提示等轻量提示不拆页面，只在HTML交互规则中说明。
- 同个对象的新增、编辑、查看默认共用同一个页面、弹窗或抽屉；只有展示内容明显不同时，才拆为不同页面。
- 三级菜单下用于承载独立业务层级的Tab菜单需要独立编号；页面内容中的普通Tab不单独编号。
- 表单、详情、弹窗、抽屉通常通过页面操作进入，不作为独立菜单入口。
- 页面内轻量入口如果进入页面总览表，入口方式必须写清所属主页面、触发按钮和打开容器；如果只作为主页面区块中的普通操作，则写入主页面内容区块和关键交互，不单独列为独立菜单页面。

## 5. 代码环境读取规则

### 5.1 触发读取条件

出现以下任一情况时，必须读取相关代码作为输入：

- 当前工作环境存在Demo代码仓库，且用户希望基于现有Demo继续设计或Coding。
- 用户明确指定代码范围、文件路径、页面模块或已有菜单。
- Product Design提到可参考的产品模块、页面或组件。
- 需求明显是在已有产品页面上新增、改造或组合能力。

### 5.2 重点读取内容

优先读取：路由配置、菜单配置、页面入口、相似模块页面、表格/表单/详情/弹窗/抽屉组件、Mock数据、状态枚举、交互处理、样式规范和组件库使用方式。

读取代码的目的不是分析后端实现，而是校准以下设计决策：

- 是否复用已有页面，还是新增菜单或Tab。
- 页面名称、菜单层级和导航路径是否与现有产品一致。
- 新增/编辑/查看应使用页面、抽屉还是弹窗。
- 搜索、筛选、表格、分页、状态标签、二次确认和Toast反馈是否沿用已有实现习惯。
- Mock数据结构、字段命名和前端状态更新方式是否与现有Demo兼容。

### 5.3 读取结果使用方式

- 代码读取结论只作为页面设计、交互说明和Coding指导的输入，不把接口、数据库、任务调度等后端技术细节写成页面功能。
- 如果代码与需求或Product Design冲突，优先把冲突列入待确认问题，并写明当前默认假设。
- 如果代码范围不明确但可能影响设计，在待确认问题中提醒用户指定参考模块。

### 5.4 代码可用状态标记

读取代码后，必须为当前任务标记代码可用状态并写入 Design Context：

- `verified`（已核验）：已实际读取并验证相关页面、组件、路由、交互和数据结构；
- `partial`（部分可用）：只读取了部分代码，仍有页面、组件或交互未验证；
- `unavailable`（不可用）：没有可用业务代码，或没有找到相关参考页面。

约束：

- 项目目录存在不代表代码已读取；只有实际读取并验证过的对象才能标记为 `verified`。
- `partial` / `unavailable` 状态下，设计说明书只能描述设计语义和组件能力（如标准列表容器、业务策略列表框架、业务对象展示组件、标准状态切换组件、标准高风险确认链路），禁止虚构真实文件路径、组件路径、Props、Events 或调用方式；真实代码对象统一标记为“Coding 阶段待核验”。
- 代码状态不阻断需求设计；设计说明书必须明确区分语义级描述与 Coding 阶段待核验对象。
- “Coding 阶段待核验”标记仅存在于设计说明书阶段；Implementation Mapping Gate 完成后，必需复用对象必须被映射结果（已验证 / 全新开发 / 不适用 / 阻塞）替换。

### 5.5 视觉基线映射

当需求属于已有业务主题或已有页面体系时，必须把真实参考页面作为视觉和交互基线，不能只复用业务字段和数据模型而忽略已有页面的视觉结构。

视觉基线映射至少覆盖：页面容器、页面标题层级、Tab 结构、筛选区、工具栏、表格容器、表格字段展示、状态组件、操作列、按钮位置和顺序、间距、边界和空状态、高风险确认链路。

视觉基线结果写入 Design Context 和页面总览表；视觉参考页面与视觉基线范围必须在 Implementation Mapping Gate 中完成核验后才可进入 Coding，Coding 阶段必须对照该基线做视觉回归。

## 6. 对话框页面总览

### 6.1 导航结构

导航结构用于综合展示本次Demo涉及哪些产品导航，从一级菜单写到Tab菜单；它主要作为需求拆解到页面设计时的页面归属、菜单层级和导航结构位置输入。同一菜单下的页面、弹窗和抽屉只写一次，不要按页面重复输出。HTML输出物中每个页面的导航位置必须使用表格展示，表头固定为“一级导航、二级导航、三级导航、Tab页面”，避免把Tab页面误识别为菜单路径。导航位置表示页面所属菜单或Tab位置，不表示当前功能子页面名称；新增、编辑、详情、弹窗、抽屉等由主页面操作进入的非菜单页面，必须展示所属主页面的导航位置，例如“新增防火墙策略”的导航位置应停留在“防火墙策略管理”页面所属菜单，不要把“新增防火墙策略”写进导航。

菜单命名必须参考所属产品已有导航的命名规律，包括常用词尾、业务对象表达、动作前后顺序和同类页面命名方式。新增页面如果放入导航菜单，同一菜单层级或同一父级菜单下不得与已有菜单或页面重名；如果作为Tab页面，一般也不得与同一页面内其他Tab重名。特殊情况是相同名称位于不同菜单路径下，且分别承载不同菜单下的同类任务或对象管理，例如两个不同一级/二级菜单下都存在“任务管理”，可以保留相同Tab或页面名，但页面总览、导航结构和Coding计划中必须写清完整导航路径，避免实现时误挂载。

```text
一级菜单
└── 二级菜单
    └── 三级菜单
        └── Tab页面
```

HTML逐页页面基础信息中的导航位置表：

| 一级导航 | 二级导航 | 三级导航 | Tab页面 |
| -------- | -------- | -------- | ------- |
| <一级导航名称> | <二级导航名称或空> | <三级导航名称或空> | <Tab页面名称或空> |

### 6.2 页面总览表

| 业务模块 | 页面ID | 页面名称 | 页面类型 | 页面用途 | 入口方式 | 关键交互 | 设计来源 | 编码方式 |
| -------- | ------ | -------- | -------- | -------- | -------- | -------- | -------- | -------- |

页面类型列必须输出 Common Design 中的中文页面类型名（具体页面类型及其中文名以已读取的 Common Design 页面模板文档为准，如基础表格页、抽屉表单页；禁止凭 AI 经验发明页面类型），禁止输出模板 ID（如 page-table-overview）；templateId 仅用于 HTML JSON 的 templateContract 字段，不展示在页面总览表中。

编码方式应与页面级AI Coding指导保持一致，取值为`复用框架`、`直接引用`、`组件复用`或`全新开发`；页面总览表只填写当前页面的主开发方式，具体开发项细分写在页面级开发项编码指导表中。

代码可用状态为 `verified` 时，初步复用方向可引用已验证的真实页面或组件；`partial` / `unavailable` 时，初步复用方向只允许“复用已有页面”“参考已有框架”“新增页面”或“待详细设计确认”，真实代码对象标注“Coding 阶段待核验”，禁止在总览表虚构文件路径或组件名称。

页面总览表是对话框输出的最后一段主体内容。页面总览表之后，必须输出待确认问题并停止，等待用户确认；确认前不生成HTML文件路径，不继续展开逐页设计。若没有关键待确认问题，明确说明“暂无关键待确认问题，按当前页面总览继续生成HTML说明书”，然后可继续生成HTML。

## 7. 待确认问题

### 7.1 生成时机

在生成HTML设计说明书和AI Coding指导之前，必须先生成待确认问题，并放在对话框的页面总览表之后。待确认问题用于帮助用户判断会影响Demo设计和Coding准确性的关键不确定项，不写入HTML说明书。输出待确认问题后必须等待用户确认，确认前禁止直接生成完整HTML和AI Coding指导。

### 7.2 筛选原则

只保留符合以下任一条件的问题：

- 影响导航结构：新增菜单、复用已有菜单、作为Tab、菜单层级变化或命名冲突。
- 影响页面容器：独立页面、抽屉、弹窗、详情页或配置页的选择。
- 影响用户旅程闭环：入口、完成任务后的返回位置、审批/提交/处置闭环、旅程卡点或断点。
- 影响关键业务规则：状态流转、权限、二次确认、高危校验、处置原因、批量操作规则。
- 影响Coding实现：是否复用已有组件、Mock数据是否覆盖特定状态、是否与已有页面联动。
- 关键需求缺失：缺少入口、目标用户、核心操作结果、状态定义、关键字段或列表对象。

### 7.3 数量与格式

- 最多10个，优先控制在3-6个。
- 不问颜色、按钮位置、普通文案等低价值问题。
- 不问已经能从需求、Product Design或代码中明确判断的问题。
- 每个问题必须包含“影响范围”和“当前默认假设”。
- 输出待确认问题后停止，等待用户确认或修正；用户确认后，先判断确认结果是否影响导航结构、页面总览、页面层级、入口方式、容器选择、关键交互或Coding方式。
- 若确认结果影响第三步已输出内容，必须先重新输出更新后的导航结构和页面总览表，再按更新后的内容生成HTML说明书和AI Coding指导。
- 生成HTML说明书前必须执行页面类型一致性自检：页面总览中的页面类型、页面名称和页面层级必须与HTML说明书保持一致；若用户未明确要求修改，不得擅自更改页面类型、页面结构或页面名称。
- 若页面属于分层 Tabs 页标题，线框图中的Tab必须与页面标题同一行展示，不得单独下沉为内容区Tab。
- 若没有关键待确认问题，写明“暂无关键待确认问题，按当前页面总览继续生成HTML说明书”，此时可继续生成HTML。

```markdown
| 序号 | 待确认问题 | 影响范围 | 当前默认假设 |
| ---- | ---------- | -------- | ------------ |
| 1 | <问题> | <导航结构/页面容器/用户旅程/业务规则/Coding实现> | <默认假设> |
```
