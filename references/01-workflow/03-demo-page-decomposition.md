## 1. 概览

Demo设计规格用于把需求转化为可查看、可实现、可指导AI Coding的页面设计说明。HTML说明书是用户确认后的页面实现基线，也是Coding阶段必须遵循并逐项落实的实现契约：它用于给用户确认页面范围、页面结构和显性设计决策，也用于在Coding效果不好时回溯问题来源；Coding过程中如确需偏离说明书（如代码环境不支持、业务调整），必须显式记录差异并说明原因，不得静默偏离，也不得将说明书当作可选择性参考的前期材料。对话框只展示到页面总览表；页面总览之后的逐页设计说明、交互逻辑、状态规则、Mock数据和AI Coding提示词必须进入HTML说明书。

页面类型定义为：能独立承载一个业务目标的容器，不限于狭义页面，也包括弹窗和抽屉。

## 2. 输出边界

### 2.1 对话框只输出到页面总览

对话框允许输出：

- 需求与Demo范围
- 核心用户与场景
- 体验目标（3条目标选项与一段画面感，在导航结构前输出，不写入HTML）
- 导航结构
- 页面总览表
- HTML文件路径和简短说明

### 2.2 HTML承载详细内容

以下内容必须写入HTML，不在对话框展开：

- 逐页设计说明
- 页面内容区块细节
- 可点击操作、搜索筛选、状态值、表单选项和校验说明
- 搜索筛选、重置、排序、分页规则在对应区块中的说明
- 新增、编辑、查看、删除、处置、启用、禁用等操作在对应区块或底部操作中的说明
- 二次确认、表单校验、状态反馈、极端情况在对应区块中的说明
- Mock数据要求
- AI Coding完整提示词

## 3. Demo范围过滤

需求文档可能包含商业选型、用户Playbook、技术方案、线下交付流程或外部系统操作。输出页面设计前，必须先判断哪些内容属于当前平台Demo可展示和可操作的范围。

| 类型 | 含义 | 是否进入Demo设计 |
| --- | ---- | --------------- |
| 平台内操作 | 用户在当前产品控制台中完成配置、创建、编辑、审批、提交、启用、禁用、查询、处理等操作 | 是 |
| 平台内展示 | 当前平台展示状态、结果、数据、日志、告警、风险、进度、详情等 | 是 |
| 线下流程 | 商务沟通、客户调研、POC、售前评估、线下实施、人工交付、运营跟进等 | 否，仅作为背景或待确认 |
| 外部系统/其他平台 | 在客户系统、第三方系统、内部运营平台、工单系统、云厂商后台等完成的操作 | 否，除非当前平台需要提供入口或展示结果 |
| 技术实现 | 技术架构、网络拓扑、接口设计、数据同步、部署脚本、算法逻辑、后台任务等 | 否，仅作为理解字段、状态或数据来源的依据 |
| 商业/运营背景 | 套餐、报价、商业选型、运营方案、客户分层、服务策略等 | 否，仅作为需求背景 |

过滤原则：只将平台内操作和平台内展示进入Demo页面设计；外部系统或线下流程不直接拆页面；技术实现不拆页面；大需求必须先过滤再拆页面。

Playbook判定：需求文档中的用户Playbook需按内容实质判断归属，而非按“Playbook”名称归类。描述用户在当前产品控制台内完成某目标的操作序列的Playbook（如进入某菜单、在某个页面配置或处理某对象），其内容实质属于“平台内操作”，应作为拆解输入，从中提取导航路径、页面序列与操作步骤，用于支撑页面拆解与导航结构设计；只有描述商务沟通、销售运营、客户跟进、人工交付等非界面动作的Playbook，才作为背景或待确认信息，不拆页面。注意区分叙事视角：客户交付视角、验收视角或现场动作视角的Playbook步骤（如设备上架、拔线回接、现场巡检），即使字面上像“在系统里操作”，只要不是当前产品UI可展示、可操作、可管理的对象与动作，一律按验收语境处理，不提取为任务图输入、不拆页面。

## 4. 页面拆解逻辑

页面拆解按以下执行顺序推进，小节编号与执行顺序一致，按序阅读对应小节即可：

1. 内部推导：进入页面拆解前已完成需求理解与业务任务建模（SKILL.md Step 1.5，requirementUnderstanding 就绪，阻塞性业务理解问题已确认）；再按第 4.1 节“页面拆解内部推导链”完成从需求素材到页面候选的内部推导（需求表达识别 → 功能交付项切分 → 业务对象与任务模型 → 任务图 → 功能落位核对 → 页面职责推导 → 任务旅程彩排 → 承载形式分流），产出页面候选与职责结论；推导链中间产物不进入对话框输出。
2. 依据与页面类型确认：按第 4.2 节沿设计依据决策链路，为每个页面确认设计依据与页面类型。
3. 入口承载判断：按第 4.6 节判断各功能点的入口承载方式（独立菜单、菜单下页面、页面内轻量入口等）。
4. 目标闭环检查：按第 4.3 节检查每个页面是否形成页面目标闭环，必要时按补齐规则补全。
5. 落入页面总览：按第 4.7 节拆解规则将页面候选落为页面总览。

### 4.1 页面拆解内部推导链（不对外输出）

本节将页面拆解从需求素材到页面候选的过程显式化为一条内部推导链，用于引导拆解思考顺序，避免只按需求字面做页面模板与字段的组装。推导链的中间推导产物仅用于支撑 4.2.3 页面类型决策表和页面总览的生成，不进入对话框输出、不写入HTML说明书、不写入demo-spec JSON，也不新增校验规则。

#### 4.1.1 内部推导链

1. 需求表达识别（前置输入）：先识别输入是功能清单式、叙事式 Playbook、口述需求还是混合表达（对应 requirementUnderstanding.inputType），确认本次要解决的需求事实边界；requirementUnderstanding 已在进入页面拆解前形成（SKILL.md Step 1.5，见 07-requirement-understanding.md），actors / goals / businessObjects / tasks / stateTransitions 已结构化，阻塞性业务理解问题已在页面拆解前确认或回落；本节直接以其为输入，不在本节重新建模。
2. 功能交付项切分（强制闸门）：进入任务图前，先基于范围过滤结果完成显式切分——功能交付项为本次产品UI可管理的对象及其操作（进页面候选来源）；语境项为客户交付旅程、验收语境、现场动作、外部系统动作、技术实现与商业背景（仅背景或待确认，不拆页面）。任何页面候选都必须能回溯到至少一条功能交付项；若某页面候选仅来自客户旅程或验收描述，改归背景并删除。功能交付项来源包含三类：①需求功能交付项（需求资料明确的功能）；②设计规范补齐项（匹配 Product Design 或已读取 Common Design 时，设计规范声明为需求已建设对象/页面类型固有、必备、默认存在或成对约束、需求未提及但默认纳入的能力，见 4.2.2 与 SKILL.md“设计规范完备性补齐”）；③AI 合理补齐项（仅限可演示性基础细节，按来源标记规则标注）。①②均可作为页面候选来源。仅当某项既无需求依据、也非设计规范声明、还超出 AI 合理补齐边界时，才不得作为功能交付项。
3. 业务对象与任务模型：将功能交付项切分确认的功能交付项组织为业务对象与任务模型——复用 Step 1.5 requirementUnderstanding 的 businessObjects 与 tasks（角色/触发/对象/动作/前置条件/判断信息/结果/下一状态/异常），核对功能交付项与业务对象、任务模型的覆盖关系；页面拆解中新发现的业务缺失（动作、状态或对象未定义）回流 Step 1.5 补齐，不得在页面层自行假设业务事实。任务模型是任务图的结构化输入。
4. 任务图：从业务对象与任务模型，以及需求资料中的流程描述与操作型Playbook（仅限当前产品控制台内可管理操作）提取用户任务；任务图不能只记录“进入哪个页面、点击什么按钮”，还必须记录每条用户任务的目标、判断信息（用户依据什么做决定）、状态变化（操作前后对象状态如何流转）与结果（成功/失败/部分成功），以及每步的入口路径、操作对象与动作（查看、新增、编辑、配置、处置等）；任务图用于确定页面候选、导航路径与页面间跳转关系。
5. 功能落位核对：将功能清单逐项判断承载去向——独立页面、菜单下页面、页面内轻量入口、已有页面改造或不承载（不承载需写明理由，如属线下流程或外部系统）；功能清单颗粒度较粗时同样逐项给出去向或排除理由，避免功能点静默丢失。去向为“页面内轻量入口”或“已有页面改造”时，除页面候选外必须同时产出入口挂载点候选 entryPoint（宿主页面、宿主是否在本次范围、宿主的区块/列/模块位置、触发元素、打开容器、来源），与页面候选一并进入第 4.6 节入口承载判定；入口挂载点是独立于页面的第二类产出物，不得因其宿主已是已有页面而省略。
6. 页面职责推导：对每个页面候选回答四个问题——服务哪个用户任务、用户在此页面完成什么、为何需要独立成页面/弹窗/抽屉而非并入已有页面、页面信息如何组织（哪些信息上列表、哪些进详情或抽屉、哪些拆为Tab、哪些可下钻）；推导结论作为选择页面类型模板与设计内容区块的业务依据。
7. 任务旅程彩排：对每个页面候选做一次内部走查——用户带着什么问题进入、第一眼获取什么、下一步点什么、异常/空态如何呈现、完成后如何离开或继续（走查口径见 SKILL.md "设计师职责与体验下限"）；发现入口缺失、反馈不明、死胡同、关键信息缺失时先修正页面候选与职责结论再进入 4.2；彩排产物不进入对话框输出，其结论应可在页面类型决策表"决策理由"中回溯。
8. 承载形式分流：已读取的 Common Design 页面类型决策内容存在承载形式分流链（如双容器场景的已配置内容承载：表格承载 vs 多卡片承载）时，命中该场景的页面候选在选定模板前必须精读分流链原文，逐特征判定（字段数/数据量/视觉丰富度等）得出承载形式，并把判定结论登记到 demo-spec 的 `designContext.carrierSweep`（条目结构与校验见 04-demo-output-spec.md 11.30）；判定语义以 CD 分流链原文为准，禁止在未读分流章节的情况下直接落默认承载模板（RULE-65 校验留痕与账实一致）；未命中分流链场景的页面不产生条目。

#### 4.1.2 推导链与既有规则的衔接

- 推导链是页面拆解的第一步，产出页面候选与职责结论后，按第 4.2 节设计依据决策链路确认每页设计依据与页面类型，按第 4.6 节判断功能入口承载方式，按第 4.3 节做页面目标闭环检查，按第 4.7 节拆解规则落为页面总览。
- 推导链不改变既有约束：页面结构仍必须继承已读取Common Design / Product Design页面模板（见 4.2.4）；推导过程中超出需求明确描述的内容仍按 4.3 的允许与禁止补齐清单执行，AI补齐项必须标注来源（如“基于页面目标闭环补齐”），不得伪装成用户原始需求，不得新增无需求依据的业务模块、复杂审批链路或跨系统联动；匹配 Product Design 或已读取 Common Design 时，按设计规范补齐纳入设计规范声明为需求已建设对象/页面类型固有、必备、默认存在或成对约束的能力，标注来源 `product-design` / `common-design`（与来源文档一致）并登记可定位锚点，不得以行业惯例冒充。
- 4.2.3 页面类型决策表中的“决策理由”应能回溯到推导产物（功能交付项切分、任务图、功能落位或页面职责结论），页面候选必须可溯源到功能交付项。

### 4.2 设计依据决策链路

设计依据不是普通参考资料，而是页面设计和AI Coding必须遵循的决策链路。页面类型、页面容器、页面区块、组件组合和交互细节必须沿着以下链路逐层确认，避免Coding阶段只把页面类型当作标签而没有还原对应结构。

#### 4.2.1 读取顺序

识别设计能力时，对照 [Design Skill Resolver - 能力识别参考框架](00-design-skill-resolver.md) 的五层（Theme 主题框架 / Template 页面模板 / Feature 业务功能 / Pattern 交互模式 / Component 组件映射）自查防漏：命中才读，未命中的层记录原因但不产生读取；禁止把五层当作全量读取清单。

命中某能力后，必须**先读取该能力对应 Reference 的正文（含精确章节锚点），再据此决定页面的字段、筛选、交互与组件**；禁止仅凭索引/摘要下结构结论，更禁止用“当前代码现状”或“Common Design 惯例”替代**已命中的 Product Design 规则**。读取结果按锚点登记进 `readLedger`（格式见 [00-design-skill-resolver.md](00-design-skill-resolver.md) §3.0），未精读的章节不得作为设计依据。

1. 用户确认的需求事实（需求资料）：优先提取需求中已确认的页面、菜单、字段、操作、流程、状态、限制、用户任务和业务规则，用于确定本次要解决的问题、平台内操作范围、页面目标和关键字段；需求事实经 Step 1.5 建模与来源标记后即为最高优先业务依据。
2. Product Design 业务事实：页面拆解和导航结构设计后，如果存在Product Design，必须优先查阅其中的产品介绍、页面导航结构、页面说明、页面设计规范和同类模块设计规则，校准菜单层级、命名、页面归属、页面类型、容器选择、字段表达、筛选搜索方式和弹窗/抽屉等交互方式；如果Product Design明确规定页面结构、筛选方式或组件方式，优先遵循Product Design——业务事实优先级为 Product Design > 当前代码。此外，Product Design 还承担设计规范补齐（source `product-design`）：当需求已确定建设某对象/页面类型时，PD 中声明为该对象/页面类型固有、必备、默认存在或成对约束的能力默认纳入范围（设计规范补齐项），需求未提及不构成排除理由；仅当用户明确不做或与需求业务事实冲突时才剔除。
3. 当前代码作为现状证据（Demo代码环境）：如果当前存在代码仓库、用户指定代码范围、Product Design提到参考模块，或用户提到已有模块，必须读取相关代码，用于校准已有路由、菜单、页面容器、组件实现、筛选方式、状态展示、Mock数据和交互习惯；代码能证明“现在怎么做”，但不能自动证明“业务应该怎么设计”，不作为业务事实的优先来源。
4. Common Design：如果存在Common Design，必须读取其中的页面类型模板、组件映射表、组件形态使用判定（widget patterns，`references/03-patterns/03-widget-patterns/`，目录级索引 + 命中控件对应文件精读）和通用设计规则，用于确定页面骨架、组件选择与组件形态、筛选方式和交互基线；Common Design是正式页面设计阶段的必需依赖，未查询到Common Design或查询到但无法成功读取其SKILL.md时，不得使用AI自身通用设计知识模拟，应停止进入正式页面设计并提示缺少Common Design。
5. AI业务理解：仅在用户资料、Product Design、Common Design和Demo代码环境未覆盖时，用于补足Demo可演示和Coding所需的基础细节；不得覆盖前面已经明确的依据，不得引入无需求依据的复杂业务能力。

#### 4.2.2 每类依据负责什么

| 依据 | 决定什么 | 不决定什么 |
| ---- | -------- | ---------- |
| 需求资料 | 用户目标、业务规则、字段、操作范围、平台内可展示和可操作内容 | 不直接决定最终页面布局和组件实现 |
| Demo代码环境 | 路由习惯、菜单配置、组件实现方式、Mock结构、交互习惯、样式模式 | 不新增需求中没有的业务能力 |
| Product Design | 产品导航、页面规范、页面类型、页面容器、组件习惯、筛选方式、产品固有字段、字段配置方式和字段展示形式；该对象/页面类型固有、必备、默认存在或成对约束的能力补齐（设计规范补齐 source `product-design`，默认纳入范围） | 不覆盖用户明确提出的新需求；但需求“未提及”不等于“明确不做”，需求沉默不构成对设计规范补齐的排除 |
| Common Design | 页面类型模板、组件映射、页面骨架、筛选方式、按钮顺序和通用交互基线；对需求已建设对象/页面类型声明为固有、必备、默认存在或成对约束的能力补齐（设计规范补齐 source `common-design`，如“支持手动新增则须支持手动删除”，默认纳入范围） | 不覆盖用户明确提出的新需求和Product Design明确的覆盖规则 |
| AI业务理解 | 修正需求中缺失但从产品专业性、行业通用设计和用户体验友好程度看需要完善的基础内容，如缺失状态、边界、Mock数据、校验提示和可演示细节 | 不覆盖明确依据，不偏离需求设定范围做过多发挥，不新增复杂业务能力 |

补充约束：

- 需求资料不仅用于提取页面、字段和操作，还用于确认业务对象、任务目标、状态变化、结果定义和权限约束；这些业务事实在 Step 1.5 建模时确认并落入 requirementUnderstanding，缺失部分作为业务理解问题在页面拆解前提出。
- AI业务理解只能推导信息组织、页面承载和交互表达，不能凭行业经验新增业务对象、状态、权限、审批或数量限制等业务事实；此类业务事实只能来自用户确认的需求事实或 Product Design。
- 设计规范补齐项只能来自匹配 Product Design 或已读取 Common Design 的明确规则（须登记可定位锚点，标记 `source: product-design` / `common-design`，与来源文档一致），不得以行业惯例或 AI 经验冒充；仅对需求已建设的对象/页面类型补齐；两类均无此类声明时不产生设计规范补齐项。


#### 4.2.3 页面类型决策表

进入页面总览前，必须为每个页面形成内部页面类型决策表。该表用于固定页面类型选择依据和后续继承关系，不要求在对话框完整展示；只有页面类型不确定且影响页面结构、用户旅程或导航时，才将问题进入待确认。表中承载形式判定结论（如双容器场景的表格承载 vs 多卡片承载）须逐页登记到 demo-spec 的 `designContext.carrierSweep`（条目结构与校验见 04-demo-output-spec.md 11.30），由 RULE-65 校验留痕完整性与选型账实一致——承载形式是页面骨架选型的一部分，跳过分流判定或只写结论不落账同样视为未完成本表。

| 字段 | 要求 |
| ---- | ---- |
| 页面ID与业务场景 | 对应页面总览，说明用户要完成的任务、入口上下文及其来自的功能交付项（见 4.1.1 功能交付项切分）；仅来自客户旅程或验收语境的候选不进入本表，应改归背景 |
| PRD/用户约束 | 记录明确的容器、流程、字段、状态或操作约束 |
| Product Design覆盖 | 记录是否存在匹配规则及其`inherit / extend / override`关系；无匹配时明确为“未匹配，使用Common Design模式” |
| 产品规则落实清单 | 逐条列出该页命中的 Product Design / 产品 Pattern / Feature 规则及其在本页的落实位置（字段、区块或交互），并登记对应 `designReferences`（`source: product-design` 且标注 `ability`）；无命中时明确为“无产品规则命中”（RULE-43 `ABILITY_SOURCE_NOT_REGISTERED` 校验） |
| 设计规范补齐 | 记录该页由匹配 Product Design 或已读取 Common Design 声明为固有/必备/默认存在/成对约束、需求未提及但默认纳入的补齐项，及其来源（`product-design` / `common-design`）与落点 landingRef（页面/区块/操作或开发项）；无补齐时明确为“无设计规范补齐” |
| Common Design候选模板 | 仅列出已实际读取的标准页面类型模板 |
| 代码证据 | 记录已验证的相似页面、组件、路由或容器结构；无证据时明确标注 |
| 最终页面类型 | 使用 Common Design 标准页面类型中文名（如概览表格页、详情抽屉、表单抽屉），不得使用业务描述或模板 ID（如 page-table-overview）替代页面类型；若 Product Design 自定义了页面模板且声明覆盖（override），则以 Product Design 页面模板为准 |
| 决策理由 | 说明最终模板如何满足业务场景、PRD约束和已有实现 |
| 未决问题 | 仅记录会影响页面类型选择的不可推断事实 |

页面类型必须使用已读取Common Design、匹配Product Design或已验证代码中真实存在的页面模板名称。不得使用未在这些依据中出现的页面模板名称。若需求需要的页面结构无法匹配已有模板，统一标记为“自定义页面类型”，并说明继承的基础模板、扩展内容、结构差异及其来源。页面类型中文名与 templateId 的唯一真值源是模板注册表（references/02-template-contracts/common-design-template-registry.json）的 `name` 字段；弹窗与抽屉不再称“页”（列表弹窗 list-modal、列表抽屉 list-drawer、详情抽屉 detail-drawer、日志详情抽屉 log-detail-drawer、表单弹窗 form-modal、表单抽屉 form-drawer），历史名“步骤条配置页”“仪表盘页”已分别改为“下钻步骤条配置页”“Dashboard”。Product Design 自定义页面模板时，页面 `type` 仍写其自定义类型名需以 `templateId=custom` + `baseTemplateId`（注册表标准模板 ID）+ `override` 声明为前提；否则须使用注册表中的标准类型名，禁止把 Product Design 自定义模板 ID 直接写入 `templateId`（RULE-04 阻断），禁止把未注册类型名写入 `type`（RULE-06 阻断）。

#### 4.2.4 页面类型强制继承规则

页面类型不是页面标题旁的标签，而是页面结构硬约束。一旦页面类型确定，HTML设计说明书和Coding实现必须继承用户资料、Product Design或已有代码中明确的对应布局、区块顺序和组件组合；只有用户明确要求覆盖时，才允许调整。

每个页面类型对应的必需结构、区块顺序与组件组合一律以已读取的 Common Design 页面模板文档为准（若 Product Design 声明了页面模板覆盖，以 Product Design 为准），本 Skill 不保存各页面类型的结构清单，避免与 Common Design 不同步；读取页面模板文档时按 00-design-skill-resolver 的能力识别参考框架确认命中并读取对应模板条目。

HTML逐页说明中必须在页面基础信息里写明“页面类型还原要求”，并描述页面骨架组件。页面类型还原要求必须同时写明页面模板中文名与页面模板 ID，格式如“概览表格页（模板 ID：page-table-overview）”；模板 ID 取自模板注册表（references/02-template-contracts/common-design-template-registry.json）或 Design Context 中已声明的 Product Design override 模板，并与 templateContract.templateId 完全一致，禁止写历史旧模板 ID。页面模板被 Product Design 声明 override 时，直接采用 Product Design 定义的页面模板中文名与模板 ID（视为注册表新增模板，不再保留 Common Design 底层 ID），补注 templateBase=product 与模板出处锚点；自定义页面类型标注 templateId=custom 与基础模板 ID。页面骨架组件信息从所采用模板的文档原文获取（Common Design 模板页取 Common Design 页面模板，PD override 模板页取 productTemplateRef 指向的模板文档），只列标题栏、Tab、筛选区、工具栏、表格、分页、弹窗、抽屉、底部操作等骨架组件，不负责列出全部字段组件。

#### 4.2.5 HTML线框图绘制规则

如果HTML说明书中生成Wireframe / ASCII线框图，线框图必须继承用户资料、Product Design或已有代码中明确的当前页面类型结构，并从该页面类型对应的设计库模板文档读取模板结构与线框样式：匹配Product Design声明了页面模板时按Product Design定义的页面模板（按 00-design-skill-resolver 的覆盖关系），否则按Common Design页面模板文档（如 02-template/01-page-types.md 的对应模板条目）。页面类型不是线框图标题标签，而是线框图布局约束；本Skill不保存任何页面模板线框图参考，模板样式一律以运行时可读取的Common Design或匹配Product Design模板文档为准。

绘制线框图前，必须先确认用户资料、Product Design或已有代码中对应页面类型的页面结构和页面元素说明，并读取Common Design或匹配Product Design模板文档中该模板的布局样式。线框图必须严格按所选模板的布局结构绘制，只允许替换文案并完善内容区中的具体内容，禁止调整模板布局结构、区块顺序、容器形态或新增模板不存在的区域；不得仅根据页面名称、页面目标或AI经验自行组合线框图。

线框图绘制顺序：

1. 先根据页面类型继承基础页面结构，例如基础表格页、概览表格页、左树表格页、配置表单页、表单抽屉、表单弹窗、详情抽屉或下钻详情页等。
2. 再按已确认的页面元素规则补充标题栏、工具栏、筛选区、表格、表单、底部操作、Tab、返回入口、关闭入口等通用部件。
3. 最后填入当前业务页面的字段、指标、按钮、状态、可点击操作和功能点入口。

页面内容区块、Wireframe / ASCII线框图和页面级Coding还原要求必须三者一致，并与页面类型决策表中的最终类型和模板依据一致。如果页面内容区块与已确认的页面类型结构冲突，优先修正页面内容区块；如果Product Design或已有代码明确覆盖页面结构，则以Product Design或已有代码为准，并在`wireframeNote`或页面类型还原要求中说明原因。

线框图绘制时禁止：

- 只画一个空白卡片或通用容器。
- 将抽屉或弹窗画成普通页面卡片。
- 将左树表格页画成普通表格页。
- 将概览表格页画成只有表格、没有概览区。
- 忽略已确认页面类型要求的标题栏、筛选区、工具栏、分页、底部按钮、关闭入口或返回入口。
- 将线框图画成"每行一个区域名：内容"的标签罗列样式（会被校验器以 RULE-34 阻断）。
- 把表格关联按钮（批量操作、其他子功能入口按钮，如新增/导入/导出等）绘制在表格框下方或表格工具栏之外的区域；归属表格的按钮必须统一置于表格区左上角工具栏（否则被校验器以 RULE-51 告警），详见 references/01-workflow/04-demo-output-spec.md 第11.16节。
- 将列设置/列配置绘制为独立按钮：列设置为表格组件自带功能（同分页、排序），线框图与按钮说明均不得单独绘制，Coding 时由表格组件自带能力提供（绘制后被校验器以 RULE-51 的 WIREFRAME_COLUMN_SETTING_DRAWN 告警）。
- 在本Skill内自建或引用页面模板线框图样式；模板样式以运行时可读取的Common Design页面模板文档为准。
- 线框图内容与页面内容区块描述不一致。

生成HTML的JSON中，每个页面对象必须写入`wireframe`字段；如需解释容器关系、Tab层级、固定底部栏、页面类型继承关系或Product Design覆盖原因，写入`wireframeNote`字段。`wireframeNote`应说明线框图参考的页面类型和结构依据，例如“线框图按基础表格页绘制，包含筛选区、工具栏、表格和分页”。

#### 4.2.6 页面目标闭环检查

页面拆解和HTML说明生成前，必须检查每个页面是否形成目标闭环，避免只按需求字面翻译导致页面无法完成用户任务。闭环检查拆成两层、按序验证：

- 业务任务闭环：先验证该页面承载的业务任务在业务层面成立——业务对象已定义且可管理、动作完整（查看/创建/维护/处置等）、状态变化成立（操作前后状态可达且不矛盾）、结果已定义（成功/失败/部分成功分别是什么）；业务任务不成立时回流 Step 1.5 补齐业务事实（对象、动作、状态、结果），不得在页面层自行假设业务事实。
- 页面目标闭环：业务任务成立后，再验证页面是否能承载该业务任务——对象管理类页面是否具备支撑对象生命周期的基础承载能力；流程/任务类页面是否具备开始、执行、结果和异常反馈；分析/事件类页面是否具备发现、查看详情和处理路径。

先验证业务任务成立，再验证页面是否完整，避免把业务缺口误当页面缺口处理。若需求只描述局部操作，AI需要判断该操作依赖的上下文能力，并从Product Design、已有代码或AI业务理解中按需补齐。补齐内容必须标注为`基于页面目标闭环补齐`，且不能伪装成用户原始需求。会明显影响页面结构、业务规则或用户旅程的补齐项应进入待确认问题。补齐内容仅限于确保页面可用、易用、可演示，不得新增业务模块、复杂审批链路、跨系统联动或与需求目标无关的高级能力。

#### 4.2.7 冲突处理规则

当多个依据冲突时，按以下规则处理：

1. 用户明确要求 > Product Design > Common Design > Demo代码环境 > AI业务理解。
2. 页面主结构冲突时，以Product Design和页面类型强制继承规则为准。
3. 局部功能点冲突时，以Product Design或已有代码为准，但不得破坏页面主结构。
4. 组件实现冲突时，按具体实现优先级处理：用户或HTML明确要求复用的对象 > 当前代码环境中已验证的业务组件和页面框架 > Product Design推荐的具体实现 > Common Design推荐组件 > 通用iDux组件语义推断 > 全新开发；设计语义优先级（Product Design > Common Design > AI补齐）只决定设计知识来源，不决定实际复用对象。Demo代码环境中已有真实可用的同名业务组件时，必须优先于设计库推荐组件纳入复用判断。
5. 筛选搜索方式冲突时，以Product Design或Common Design页面模板明确说明为准；Product Design未说明时，再参考代码环境、主题类设计和基础设计规则。
6. 若冲突会影响导航、页面总览、页面容器、核心旅程或Coding实现，必须进入待确认问题。
7. 需求沉默不等于排除：需求未提及、但匹配 Product Design 或已读取 Common Design 声明为需求已建设对象/页面类型固有、必备、默认存在或成对约束能力的内容，默认纳入范围（设计规范补齐）；仅当用户明确表示不做或与需求业务事实冲突时才剔除，并记录排除原因。

### 4.3 页面目标闭环检查

页面拆解和HTML设计说明生成前，必须检查每个页面是否形成目标闭环。不要只做需求字面翻译；当需求只描述局部操作、功能目标、业务效果或流程时，AI需要判断该页面是否已经能支撑用户完成完整任务。检查按两层进行：先验证业务任务闭环（对象、动作、状态、结果是否成立），再验证页面目标闭环（页面能否承载上述业务任务），避免把业务缺口误判为页面缺口。

检查问题：

1. 页面目标闭环：用户进入页面后要完成什么任务，页面是否能支撑用户完成这个任务。
2. 对象生命周期闭环：如果页面承载一个业务对象，是否能支撑对象从查看、定位、创建、维护到结果确认的基础管理生命周期。
3. 流程闭环：如果页面承载一个流程，是否能支撑流程的开始、执行、结果和异常处理。
4. 分析闭环：如果页面承载分析场景，是否能支撑发现问题、查看详情和进一步处理。
5. 数据闭环：列表字段、详情字段、表单字段、状态字段、操作结果之间是否能互相解释，避免列表展示了数字但无法查看明细。
6. 状态闭环：加载、空数据、无权限、禁用、失败、成功、处理中等关键状态是否补齐，避免交互断点。

当页面目标不闭环时，应从用户需求上下文、Product Design、已有代码习惯和AI业务理解中补齐必要内容。补齐不是新增一套设计规则，也不是自由发挥，而是为了让页面目标完整、Demo可用、Coding可落地。

允许补齐：支撑页面目标完成的基础入口；支撑对象生命周期闭环的基础操作；支撑流程闭环的状态和结果；支撑Demo可演示的反馈、空状态、异常态和边界情况；匹配 Product Design 或已读取 Common Design 时，还包括设计规范声明为需求已建设对象/页面类型固有、必备、默认存在或成对约束、需求未提及但默认纳入的能力（设计规范补齐项）。

禁止补齐：新业务模块、新复杂流程、新审批链路、新跨系统联动、新角色权限体系，以及与需求目标无关的高级能力。设计规范补齐项的来源是匹配 Product Design 或已读取 Common Design 的明确规则，不属于此处禁止的“新业务模块”。

补齐内容应在页面总览、页面内容区块或页面级Coding建议中标注来源：`基于页面目标闭环补齐`。如果补齐内容会明显影响页面结构、业务规则、核心用户旅程或Coding实现，应进入待确认问题；如果只是字段命名、按钮文案、普通筛选项、常规状态反馈等可由AI合理补齐的内容，不要全部列为待确认问题。

反例：服务器管理只输出新增表单，没有列表承载和新增后的结果确认；告警事件分析只有事件列表页，没有事件详情页，导致用户无法完成分析任务；配置表单中必填下拉没有默认选项或选项来源，导致用户无法提交配置；表格中展示“关联规则组数量”，但点击后无法查看具体规则组，导致信息链路断开。

正确做法：对象管理类页面需要补齐支撑对象维护的基础承载能力；分析类页面需要补充详情页、详情抽屉或分析面板；配置类页面需要补齐默认值、选项来源、校验反馈和保存结果；列表中的聚合数字、对象数量、命中次数等可点击信息，需要补充明细查看方式。

表单布局口径（适用于**所有含表单配置的页面**：配置表单页、下钻步骤条配置页的表单步骤、表单弹窗、表单抽屉，不限于"配置类页面"）：表单配置项一律**单列**——每行一个配置项，label 在左、控件在右、水平同一行；禁止把两个及以上配置项画在同一行，禁止 label 独占一行而控件在下一行。容器形态（弹窗/抽屉/页面）不改变该口径。表单布局真值以已读取的 Common Design 表单规范为准（本 Skill 不内置表单布局真值），结论须锚点级登记到 `codingGuide.designReferences` 并在 `readLedger` 命中 `status=read`；线框违反单列口径或依据未登记/未精读会被 RULE-57 告警（warning，详见 04-demo-output-spec.md 11.22）。**动态表单列表例外**：绑定条件、映射规则、审批条件等动态列表/行内可编辑表格（IxProFormList）本就是“一行一个对象、一行多列”，不适用单列口径——拆解时区块声明 `formList: true`（或页面级 `formListBlocks` 登记区块名），ascii 按列头 + 一行一条记录绘制、行尾带行内删除/移除标记；未声明豁免时同行多字段且带删除标记的行也会被自动豁免，未声明且无删除标记的同行多配置项仍按违规告警。控件形态（下拉面板变体、标签样式等）不在此口径内，按 RULE-54 依 Common Design widget patterns 判定。**平铺筛选组件顺序**：筛选方式为平铺筛选项时，组件从左到右固定「时间/日期范围 -> 下拉选择类（状态/类型等）-> 搜索框（关键字输入）」，搜索框固定最右、禁止置首；PRD 或 Product Design 明确指定其他顺序时在页面 filterOrderOverride 声明说明（画反会被 RULE-61 告警，warning，详见 04-demo-output-spec.md 11.26）。

复用业务组件容器口径（**不改动页面拆解逻辑，只影响"拆解后是否单独描述"**）：拆解出的弹窗/抽屉/子页面若命中 Product Design 业务封装组件（或代码识别已明确知道的业务封装功能），且属于**需求延伸容器**（由宿主页面动作触发：按钮点击、表格字段点击、详情字段点击、行操作、导入、导出），则该容器不单独描述——不画线框图、不写页面内容区块与底部操作，只在宿主页面写一句"点击 X 打开 Y（复用 <组件名>，不单独绘制）"，容器保留一条 `mode=reuse` 的开发项指向业务组件，并把 Product Design 组件依据锚点级登记、精读留痕（详见 04-demo-output-spec.md 11.24，RULE-59）。**需求直接点名的页面（主页面）不适用**：主页面必须完整拆解并产出线框图与内容说明；识别不清时按"仍需要完整产出"处理，不要靠猜判定复用——自绘样式与业务实现不一致会误导编码，误判为复用则会丢失必要设计。

### 4.4 Product Design识别方式

Product Design统一指包含业务基础产品介绍、页面导航结构、页面设计规范和相关页面说明的Skill，不再区分业务知识库Skill。

识别方式：

- 通过当前环境的Skill查询能力查找声明`skill_type: product-design`且需求产品名命中其任一产品标识的Skill；
- Product Design 通过 metadata 的 `product_id` 声明其服务的产品标识；同一产品存在多个名称（例如 AES 与 DR 为同一产品，需求资料中可能显示为 DR，但需使用 AES 的 Product Design）时，`product_id` 允许声明逗号分隔的多个标识（如 `product_id: aes, dr`），首个为主标识，其余为同一产品的别名标识；需求产品名（主名或别名）与任一标识一致（忽略大小写与空白）即判定匹配并可调用，不得要求需求产品名必须与主标识一致；
- 产品身份必须依据 Product Design 的 metadata、product_id（含同一产品的多标识声明）或 Design Skill Resolver 结果确定；禁止通过 Skill 名称中是否出现产品缩写（如 XDR、SASE、DSP 等）猜测，也禁止在通用 Skill 内容中硬编码具体产线或产品名称；
- 未找到匹配 Product Design 时，按 Common Design、当前代码环境和明确标记的AI补齐继续设计，不阻断流程。

### 4.5 关键交互说明生成依据

页面关键交互说明必须综合以下六类信息生成：

1. 需求资料：提取明确写出的用户操作、业务流程、状态限制、字段联动、审批/处置规则、异常限制和成功结果。
2. Product Design：如果识别到Product Design，优先参考既有产品导航、页面说明、页面设计规范、弹窗/抽屉使用习惯、菜单命名和同类功能交互模式。
3. Common Design：读取其中的页面类型模板、组件映射表、组件形态使用判定（widget patterns，`references/03-patterns/03-widget-patterns/`）和通用交互规则，用于确定交互基线、反馈方式、组件习惯与组件形态选型；Common Design是正式页面设计阶段的必需依赖，未查询到Common Design或查询到但无法成功读取其SKILL.md时，不得使用AI自身通用设计知识模拟，应停止进入正式页面设计并提示缺少Common Design。
4. Demo代码环境：如果存在相关代码，读取已有路由、菜单配置、页面结构、组件组织、表单/表格/抽屉/弹窗实现、Mock数据结构和状态管理方式，校准交互落地方式。
5. AI业务理解：只有Product Design、Common Design和已有代码未覆盖时，基于B端常见页面类型、表单、表格、详情、Tab、二次确认、多层级下钻等设计手法补齐交互。
6. 补齐边界：当资料没有明确描述但Demo需要可操作、可演示、可Coding时，基于业务目标、用户任务和页面容器类型合理补齐基础交互，但不得引入无需求依据的复杂业务能力。

关键交互说明至少覆盖：触发入口、触发方式、打开容器、页面反馈、数据变化、表单校验、成功反馈、失败反馈、状态联动、空状态、加载态、无权限态和必要的极端情况。

### 4.6 功能入口承载判断

页面拆解时，先判断每个功能点的入口承载方式，再决定是否进入页面总览表。不要只根据功能名称看起来“可独立管理”就默认新增菜单、Tab或完整页面。

承载/编排类对象的主从默认判定：当需求的主要对象是承载或编排类能力（如隧道、桥、映射、策略等以承载配置为功能本体的对象）时，默认以承载对象的管理页面为主页面结构（列表、详情、新建、编辑构成对象生命周期主线），客户旅程或使用场景叙事只作为入口上下文或对象关联入口，不作为主流程页拆解依据；仅当PRD明确以向导或编排流程为主流程页时，才以流程页为主结构。该默认判定不替代 4.6.1~4.6.3，承载对象下的子功能入口方式仍按本节规则判断。

#### 4.6.0 需求线索触发清单（防漏）

当需求主体描述中出现以下线索词时，必须显式输出对应的承载结论，不得只凭功能名称判断，也不得静默跳过：

| 需求线索（出现在需求主体描述中） | 必须输出的承载结论 |
|---|---|
| “链接”“点击…打开”“查看…详情” | 入口容器（弹窗 / 抽屉 / 下钻页 / 详情页）与进入方式 |
| “在…时提供”“支持…配置”“可设置…” | 入口归属（页面内按钮 / 工具栏 / 行内操作 / 独立菜单），并说明为何不拆独立菜单 |
| “可选择 N 个”“支持批量”“多选”“全选” | 选择容器（表格行选择 / 列表页选择 / 穿梭框）与批量操作的落点 |
| “按…筛选”“可搜索”“可按…查询” | 筛选区承载（平铺筛选 / 高级搜索）与筛选控件来源 |
| “上传”“下载”“导入”“导出” | 触发入口与结果反馈落点 |
| “定时”“周期”“触发条件” | 配置入口与规则承载位置 |

命中任一线索但未在页面总览或区块说明中输出对应承载结论，视为漏项，须在质量自检中修正。

#### 4.6.1 优先作为独立菜单或菜单Tab的情况

满足以下任一条件时，优先考虑独立菜单、已有菜单下新增页面，或菜单Tab：

- 功能本身是用户高频进入的核心任务。
- 功能有独立业务目标和完整用户旅程，例如查看列表、筛选、详情、处置、配置、结果追踪。
- 功能需要稳定导航入口，用户需要反复进入。
- 功能包含较多对象管理能力，例如列表、新增、编辑、删除、批量操作、详情、状态流转。
- 功能需要承载多类子能力，弹窗或抽屉无法清晰表达。
- Product Design、已有代码或用户明确要求放入导航菜单或Tab。

#### 4.6.2 优先作为页面内按钮或工具入口的情况

满足以下多数条件时，不要默认拆成独立菜单或独立页面，优先放在相关对象或相关页面中，作为页面内按钮、工具栏按钮、行内操作或详情区操作入口：

- 功能属于非核心旅程中的辅助配置、全局配置或对象关联配置。
- 用户通常是在处理某个对象或某个主页面任务时才需要进入该功能。
- 功能不需要用户长期高频单独访问。
- 功能本身没有完整独立旅程，只是为了辅助主页面完成配置。
- 配置对象少、字段少、状态少，主要是新增、编辑、选择或关联。
- 功能与某个已有页面或对象强相关，例如在策略页配置标签、在线路页配置带宽保护、在资源页选择地址池。
- 如果单独放菜单，会让导航膨胀或割裂用户任务。

非核心配置的轻量入口适用于标签管理、带宽保护设置、全局地址池管理等辅助配置、全局配置或对象关联配置。这类能力通常不需要单独起菜单，优先将入口放在相关对象或相关页面中，通过页面内按钮或工具入口触发，并由弹窗、抽屉或必要的下钻页面承载。

#### 4.6.3 页面内入口的容器选择

当功能判断为页面内轻量入口后，按以下规则选择容器：

- 表单弹窗：配置内容少、字段少、一次性完成、不需要保留复杂上下文。
- 表单抽屉：配置内容中等复杂、需要保留当前页面上下文、需要展示对象摘要或配置分组。
- 列表弹窗：需要临时选择对象，列表简单，选择后立即回到当前任务。
- 列表抽屉：需要选择或查看较多对象，并且需要保留当前页面上下文。
- 下钻页面：配置内容复杂、字段多、需要多区块、多Tab、长时间编辑、稳定URL或独立保存流程。

#### 4.6.4 正反例

- 正例：在策略管理页中给策略绑定标签，不单独拆“标签管理”菜单，优先在策略表格工具栏或行内操作中提供“标签管理”或“设置标签”按钮，打开表单弹窗或表单抽屉。
- 正例：在线路配置页中设置带宽保护，如果只是给当前线路补充保护参数，优先作为线路详情或编辑页中的“带宽保护设置”按钮，打开表单抽屉。
- 正例：在资源分配页中选择全局地址池，如果只是临时选择地址池对象，优先使用列表弹窗或列表抽屉，不单独拆地址池导航。
- 反例：标签本身有完整管理能力，包含标签列表、创建、编辑、删除、批量导入、权限控制和引用分析时，可以考虑独立菜单或Tab，而不是仅作为弹窗入口。
- 反例：地址池需要长期维护、被多个模块复用、存在容量监控、状态流转和批量操作时，应考虑独立配置页面或菜单Tab。

#### 4.6.5 入口承载判定（宿主落位，含范围外宿主）

4.6.1~4.6.3 判断的是入口“用什么容器承载”，本节判断入口“落在哪个页面的哪个位置、以及宿主页面不在本次范围时怎么办”。任何被判定为“页面内轻量入口”或“已有页面改造”的功能点，都必须先完成入口承载判定，产出入口挂载点（entryPoint），再把结论写入页面总览、页面区块与线框图。

先判定宿主页面是否在本次页面范围内（hostScope）：

- `in-scope`：宿主页面是本次要做的页面（含本次新增的页面）。入口必须落到宿主页面的具体位置——写清宿主页面的区块 / 列 / 模块、触发元素（按钮 / 行内操作 / 工具栏 / 图标）与点击后打开的容器；该入口必须同时进入宿主页面的内容区块（`sections` 的按钮/可点击操作）或页面 `operations`（`open-container` 指向该容器），并在宿主线框图中绘制出来。
- `out-of-scope`：宿主页面是既有的、本次不做的页面（如“在安全事件页告警列表加入一条行为白名单规则”中的安全事件页）。此时不得把入口伪装成一个独立新页面蒙混过关，必须强制完成四条：
  1. 宿主登记：宿主以 `entryHost` 登记（写入顶层 `entryHosts`，见 references/01-workflow/04-demo-output-spec.md 第 11.17 节）；范围外宿主不进入 `pages`、不进入导航结构，只出现在入口清单中，避免污染本次页面范围。
  2. 精读宿主：对范围外宿主做 Tier 1 精读（见 SKILL.md 代码读取分层），确认宿主页面级结构（Tab 集合、区块构成、操作列现状），以便入口融入既有形态。
  3. 宿主入口落位：in-scope 宿主（本次范围内的页面）在本页线框图中绘制入口触发元素并以显式标记（如 `【xx入口】`）标注，画出点击后打开的容器关系，不得只画入口自己的容器；out-of-scope 宿主（既有页面）**不重绘宿主线框图**，改为在 `entryHosts[].wireframe` 登记一行宿主落位说明（宿主内位置 + 触发元素 + 打开容器 + 编码要求），例如"宿主：安全事件页/告警列表；位置：操作列；触发：加入行为白名单；打开：行为白名单表单抽屉 P003；编码要求：操作列追加按钮并绑定 P003-E01"。
  4. 建立开发项：为入口建立对应开发项（挂在打开容器页面的 `codingGuide.pageItems` 下，`scope` 用 `entry-point`），并把开发项 ID 写入 `entryHosts[].devItem`，确保编码阶段不漏做、核销清单能覆盖。

统一约束：每个入口挂载点都要在顶层 `requirementEntryPoints` 逐条声明（字段见 references/01-workflow/04-demo-output-spec.md 第 11.17 节）；只要 PRD 点名入口，无论宿主是否在范围内都不得省略声明。入口的容器（弹窗 / 抽屉）仍按 4.6.3 与页面拆解规则作为独立设计对象（表单弹窗 / 列表抽屉等）出现在 `pages`；入口挂载点是对“该容器从哪里打开”的补充，二者不可互相替代。

#### 4.6.6 宿主页面定位与消歧（防张冠李戴）

定位宿主页面（或任何“复用 / 相似页面”）时，**禁止以文件名 / 目录名作为判定依据**，必须用导航路径逐级对证，避免形近 / 近义命名导致的错配（典型：`alert-list` 实为“告警链”，而“告警列表”是 `alarm-list`）。

定位四步（缺一不可）：

1. 抽取路径：从 PRD 抽取逐级导航路径与目标语义（如“安全事件 → 事件详情 → 告警列表”）。
2. 检索身份源：在路由 / 菜单配置中按该路径逐级检索（环境无代码或不完整时，退化为以页面标题 / 组件导出名 + 侧边栏 / Tab 文案对证）。
3. 枚举候选：列出所有形近 / 近义候选（如 `alert-list`、`alarm-list`、`event-list`），逐个打开确认其归属层级、Tab 与标题。
4. 对证排除：仅“导航路径 + 标题 / Tab 语义”均命中 PRD 的候选为宿主；逐条记录被排除候选及理由；找不到完全匹配时必须显式声明“未能确认”，严禁降级为文件名匹配。

产出要求：每个定位到的既有页面都要在 `requirementEntryPoints[].hostEvidence`（或 `pageIdentityRefs[].evidence`）中登记身份证据，字段与校验见 references/01-workflow/04-demo-output-spec.md 第 11.18 节（RULE-53）。

### 4.7 拆解规则

- 独立路由、独立菜单入口或独立任务：按页面类型拆解，可拆为完整页面、表单弹窗、列表弹窗、表单抽屉、列表抽屉、详情抽屉等。
- 二次确认、删除确认、禁用确认、小i说明、悬浮提示等轻量提示不拆页面，只在对应区块的“按钮/可点击操作”表格中说明：写清触发方式、使用组件与文案（高影响操作必填二次确认文案），组件与文案优先取自 Product Design（其次 Common Design）的 pattern，格式见references/01-workflow/04-demo-output-spec.md第11.15节（RULE-50）。
- 同个对象的新增、编辑、查看默认共用同一个页面、弹窗或抽屉；只有展示内容明显不同时，才拆为不同页面。共用同一布局且 UI 完全一样（同模板、同容器类型、仅数据与标题不同）时，绘制侧同样只画一份：主页面（如新增）完整绘制线框图，从页面（如编辑）不重绘，声明 `wireframeSharedWith` 指向主页面并用 `wireframeDiff` 一句话描述差异（RULE-62 校验，见 references/01-workflow/04-demo-output-spec.md 第 11.27 节）；对象不一样（UI 不同）不得共用，仍须各自完整绘制。
- 三级菜单下用于承载独立业务层级的Tab菜单需要独立编号；页面内容中的普通Tab不单独编号。
- 表单、详情、弹窗、抽屉通常通过页面操作进入，不作为独立菜单入口。
- 页面内轻量入口如果进入页面总览表，入口方式必须写清所属主页面、触发按钮和打开容器；如果只作为主页面区块中的普通操作，则写入主页面内容区块和关键交互，不单独列为独立菜单页面。
- 入口挂载点必须逐条登记到顶层 `requirementEntryPoints`：in-scope 宿主必须落到宿主页面的区块操作或 `operations` 并绘入宿主线框图；out-of-scope 宿主必须在顶层 `entryHosts` 登记（含 Tier1 精读、宿主落位说明、开发项，不重绘宿主线框图），宿主不进 `pages`、不进导航结构（RULE-52 校验，见 references/01-workflow/04-demo-output-spec.md 第 11.17 节）。
- 入口挂载点是独立于页面的第二类产出物：同一个“新增行为白名单规则”容器，可以同时被行为白名单页的“新增”按钮和告警列表的“加入行为白名单”行内操作打开，两个入口都要各自登记，不能因为容器相同而只登记一个。

## 5. 代码环境读取规则

### 5.1 触发读取条件

出现以下任一情况时，必须读取相关代码作为输入：

- 当前工作环境存在Demo代码仓库，且用户希望基于现有Demo继续设计或Coding。
- 用户明确指定代码范围、文件路径、页面模块或已有菜单。
- Product Design提到可参考的产品模块、页面或组件。
- 需求明显是在已有产品页面上新增、改造或组合能力。
- PRD 点名要在某个既有页面上加入口或做改动（即使该既有页面不在本次页面范围内），需读取该宿主页面的页面级结构以完成入口落位。

### 5.2 重点读取内容

优先读取：路由配置、菜单配置、页面入口、相似模块页面、表格/表单/详情/弹窗/抽屉组件、Mock数据、状态枚举、交互处理、样式规范和组件库使用方式。

读取代码的目的不是分析后端实现，而是校准以下设计决策：

- 是否复用已有页面，还是新增菜单或Tab。
- 页面名称、菜单层级和导航路径是否与现有产品一致。
- 新增/编辑/查看应使用页面、抽屉还是弹窗。
- 搜索、筛选、表格、分页、状态标签、二次确认和Toast反馈是否沿用已有实现习惯。
- Mock数据结构、字段命名和前端状态更新方式是否与现有Demo兼容。

### 5.3 读取结果使用方式

- 代码读取结论只作为页面设计、交互说明和Coding指导的输入，不把接口、数据库、任务调度等后端技术细节写成页面功能。
- 如果代码与需求或Product Design冲突，优先把冲突列入待确认问题，并写明当前默认假设。
- 如果代码范围不明确但可能影响设计，在待确认问题中提醒用户指定参考模块。

### 5.4 代码可用状态标记

读取代码后，必须为当前任务标记代码可用状态并写入 Design Context：

- `verified`（已核验）：已实际读取并验证相关页面、组件、路由、交互和数据结构；
- `partial`（部分可用）：只读取了部分代码，仍有页面、组件或交互未验证；
- `unavailable`（不可用）：没有可用业务代码，或没有找到相关参考页面。

约束：

- 项目目录存在不代表代码已读取；只有实际读取并验证过的对象才能标记为 `verified`。
- `partial` / `unavailable` 状态下，设计说明书只能描述设计语义和组件能力（如标准列表容器、业务策略列表框架、业务对象展示组件、标准状态切换组件、标准高风险确认链路），禁止虚构真实文件路径、组件路径、Props、Events 或调用方式；真实代码对象统一标记为“Coding 阶段待核验”。
- 代码状态不阻断需求设计；设计说明书必须明确区分语义级描述与 Coding 阶段待核验对象。
- “Coding 阶段待核验”标记仅存在于设计说明书阶段；Implementation Mapping Gate 完成后，必需复用对象必须被映射结果（已验证 / 全新开发 / 不适用 / 阻塞）替换。

### 5.5 视觉基线映射

当需求属于已有业务主题或已有页面体系时，必须把真实参考页面作为视觉和交互基线，不能只复用业务字段和数据模型而忽略已有页面的视觉结构。

视觉基线映射至少覆盖：页面容器、页面标题层级、Tab 结构、筛选区、工具栏、表格容器、表格字段展示、状态组件、操作列、按钮位置和顺序、间距、边界和空状态、高风险确认链路。改造既有页面或在既有页面加入口时，还必须对宿主页面建立“既有形态基线”：入口所处模块（区块 / 列）的既有元素形态、相邻操作（图标 / 按钮）的样式与排列，入口必须融入既有形态而非另起一套样式。

视觉基线结果写入 Design Context 和页面总览表；视觉参考页面与视觉基线范围必须在 Implementation Mapping Gate 中完成核验后才可进入 Coding，Coding 阶段必须对照该基线做视觉回归。

## 6. 对话框页面总览

### 6.1 导航结构

导航结构用于综合展示本次Demo涉及哪些产品导航，从一级菜单写到Tab菜单；它主要作为需求拆解到页面设计时的页面归属、菜单层级和导航结构位置输入。同一菜单下的页面、弹窗和抽屉只写一次，不要按页面重复输出。HTML输出物中每个页面的导航位置必须使用表格展示，表头固定为“一级导航、二级导航、三级导航、Tab页面”，避免把Tab页面误识别为菜单路径。导航位置表示页面所属菜单或Tab位置，不表示当前功能子页面名称；新增、编辑、详情、弹窗、抽屉等由主页面操作进入的非菜单页面，必须展示所属主页面的导航位置，例如“新增防火墙策略”的导航位置应停留在“防火墙策略管理”页面所属菜单，不要把“新增防火墙策略”写进导航。

菜单命名必须参考所属产品已有导航的命名规律，包括常用词尾、业务对象表达、动作前后顺序和同类页面命名方式。新增页面如果放入导航菜单，同一菜单层级或同一父级菜单下不得与已有菜单或页面重名；如果作为Tab页面，一般也不得与同一页面内其他Tab重名。特殊情况是相同名称位于不同菜单路径下，且分别承载不同菜单下的同类任务或对象管理，例如两个不同一级/二级菜单下都存在“任务管理”，可以保留相同Tab或页面名，但页面总览、导航结构和Coding计划中必须写清完整导航路径，避免实现时误挂载。

```text
一级菜单
└── 二级菜单
    └── 三级菜单
        └── Tab页面
```

HTML逐页页面基础信息中的导航位置表：

| 一级导航 | 二级导航 | 三级导航 | Tab页面 |
| -------- | -------- | -------- | ------- |
| <一级导航名称> | <二级导航名称或空> | <三级导航名称或空> | <Tab页面名称或空> |

### 6.2 页面总览表

| 业务模块 | 页面ID | 页面名称 | 页面类型 | 页面用途 | 入口方式 | 关键交互 | 设计来源 | 编码方式 |
| -------- | ------ | -------- | -------- | -------- | -------- | -------- | -------- | -------- |

页面类型列必须输出 Common Design 中的中文页面类型名（具体页面类型及其中文名以已读取的 Common Design 页面模板文档为准，如基础表格页、表单抽屉；禁止凭 AI 经验发明页面类型），禁止输出模板 ID（如 page-table-overview）；templateId 仅用于 HTML JSON 的 templateContract 字段，不展示在页面总览表中。

编码方式应与页面级AI Coding指导保持一致，取值为`复用框架`、`直接引用`、`组件复用`或`全新开发`；页面总览表只填写当前页面的主开发方式，具体开发项细分写在页面级开发项编码指导表中。

代码可用状态为 `verified` 时，初步复用方向可引用已验证的真实页面或组件；`partial` / `unavailable` 时，初步复用方向只允许“复用已有页面”“参考已有框架”“新增页面”或“待详细设计确认”，真实代码对象标注“Coding 阶段待核验”，禁止在总览表虚构文件路径或组件名称。

匹配到 Product Design 或已读取 Common Design 时，页面总览表之后、待确认问题之前，必须输出“设计规范补齐清单”，逐项列出设计规范声明为需求已建设对象/页面类型固有、必备、默认存在或成对约束能力、需求未提及但默认纳入的补齐项（补齐能力、所属对象或页面、来源 `product-design` / `common-design` 及文档锚点、默认处理与落点 landingRef），默认处理为“纳入”，无补齐时写“无”；每个 included 补齐项须确定本次设计落点 landingRef 并同步登记到 designContext.designCompleteness（生成说明书时写入 demo-spec.json，缺失落点或落点无痕迹会被 RULE-63 阻断，见 [demo-output-spec](04-demo-output-spec.md) §11.28）；该清单只在对话框输出，不写入HTML。页面总览表与设计规范补齐清单是对话框输出的最后一段主体内容，之后必须输出待确认问题（设计决策类；业务理解类问题已在页面拆解前由 Step 1.5 提出并确认，见 [需求理解与业务任务建模](07-requirement-understanding.md)）并停止，等待用户确认；确认前不生成HTML文件路径，不继续展开逐页设计。若没有关键待确认问题，明确说明“暂无关键待确认问题，按当前页面总览继续生成HTML说明书”，然后可继续生成HTML。

当顶层声明 `requirementEntryPoints` 时，页面总览表之后（与设计规范补齐清单并列）必须输出“入口清单”：逐条列出入口挂载点的宿主页面、宿主范围（in-scope / out-of-scope）、宿主位置、触发元素、打开容器与来源；out-of-scope 宿主只在此清单出现（不进导航结构、不进 pages），并在清单中附 `entryHosts[].wireframe` 的宿主落位说明（位置 + 触发元素 + 打开容器 + 编码要求）。入口清单**同时写入 HTML 设计说明书**（生成器在页面总览后渲染“需求入口清单”区块），确保编码阶段能从说明书直接拿到宿主落位信息，不因只在对话框输出而遗漏；对话框中仍照常输出以便用户确认 PRD 点名的入口没有遗漏。

## 7. 待确认问题

### 7.1 生成时机

待确认问题按两类分时机提出：业务理解问题（业务对象、动作范围、状态定义与流转等影响业务模型理解的内容）在页面拆解前由 Step 1.5 提出，阻塞项须在页面拆解前确认（见 [需求理解与业务任务建模](07-requirement-understanding.md)）；设计决策问题（页面组织、容器、交互方式等）在本章页面总览后提出。

在生成HTML设计说明书和AI Coding指导之前，必须先生成待确认问题（设计决策类），并放在对话框的页面总览表之后。待确认问题用于帮助用户判断会影响Demo设计和Coding准确性的关键不确定项，不写入HTML说明书。输出待确认问题后必须等待用户确认，确认前禁止直接生成完整HTML和AI Coding指导。

### 7.2 筛选原则

只保留符合以下任一条件的问题：

- 影响导航结构：新增菜单、复用已有菜单、作为Tab、菜单层级变化或命名冲突。
- 影响页面容器：独立页面、抽屉、弹窗、详情页或配置页的选择。
- 影响用户旅程闭环：入口、完成任务后的返回位置、审批/提交/处置闭环、旅程卡点或断点。
- 影响关键业务规则：状态流转、权限、二次确认、高危校验、处置原因、批量操作规则。
- 影响Coding实现：是否复用已有组件、Mock数据是否覆盖特定状态、是否与已有页面联动。
- 关键需求缺失：缺少入口、目标用户、核心操作结果、状态定义、关键字段或列表对象。

### 7.3 数量与格式

- 最多10个，优先控制在3-6个。
- 不问颜色、按钮位置、普通文案等低价值问题。
- 不问已经能从需求、Product Design或代码中明确判断的问题。
- 每个问题必须包含“影响范围”和“当前默认假设”。
- 输出待确认问题后停止，等待用户确认或修正；用户确认后，先判断确认结果是否影响导航结构、页面总览、页面层级、入口方式、容器选择、关键交互或Coding方式。
- 若确认结果影响第三步已输出内容，必须先重新输出更新后的导航结构和页面总览表，再按更新后的内容生成HTML说明书和AI Coding指导。
- 生成HTML说明书前必须执行页面类型一致性自检：页面总览中的页面类型、页面名称和页面层级必须与HTML说明书保持一致；若用户未明确要求修改，不得擅自更改页面类型、页面结构或页面名称。
- 若页面属于分层 Tabs 页标题，线框图中的Tab必须与页面标题同一行展示，不得单独下沉为内容区Tab。
- 若没有关键待确认问题，写明“暂无关键待确认问题，按当前页面总览继续生成HTML说明书”，此时可继续生成HTML。

```markdown
| 序号 | 待确认问题 | 影响范围 | 当前默认假设 |
| ---- | ---------- | -------- | ------------ |
| 1 | <问题> | <导航结构/页面容器/用户旅程/业务规则/Coding实现> | <默认假设> |
```
