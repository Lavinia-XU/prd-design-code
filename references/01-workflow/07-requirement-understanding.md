## 1. 概览

本文件定义如何把叙事式需求（PRD、功能清单、Playbook、口述需求、截图或原型）转换为可支撑页面拆解的设计输入。页面拆解前必须先完成需求理解与业务任务建模，产出结构化 `requirementUnderstanding` 写入 Design Context；业务模型未理解清楚前，页面类型与页面容器决策没有可靠依据。

建模要回答的问题：谁在什么触发下，对什么业务对象做什么动作，用户凭什么信息做判断，操作前后对象状态如何变化，成功、失败、部分成功分别是什么，以及权限不足、对象不适用、执行失败等异常如何处理。

主入口执行位置：SKILL.md Step 1.5；页面拆解内部推导链引用见 03-demo-page-decomposition.md 4.1。

## 2. 输入类型识别

先判断输入属于哪种表达类型，再选择提取方式：

| 输入类型 | 特征 | 提取方式 |
| --- | --- | --- |
| 功能清单式需求 | 以功能点、模块、字段清单形式列出，按对象组织 | 从功能清单反推业务对象、动作与页面承载关系 |
| 叙事式 Playbook | 以用户操作故事、步骤序列描述完成某目标的过程 | 按第 3 节要素逐段提取，还原任务与状态 |
| 截图或原型 | 页面截图、原型图、录屏、已有 Demo | 先转写为结构化页面与字段描述，再建模其背后的业务任务 |
| 口述需求 | 口头表达，结构松散、顺序随意 | 先整理为需求要点，再判断是功能清单还是叙事表达 |
| 混合型需求 | 同时包含清单与叙事 | 以叙事段还原任务主线，以功能清单核对对象与动作完整性 |

表达类型写入 `inputType`：`functional-list`（功能清单式）、`narrative`（叙事式）或 `mixed`（混合）。截图或原型、口述需求在转写后按其主导表达方式归类。

## 3. 叙事需求提取规则

对每段叙事（Playbook / 口述故事 / PRD 场景描述）按以下要素提取：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| 角色 | 谁执行 | 安全运营人员 |
| 触发 | 什么情况下开始 | 收到事件告警、任务分派 |
| 目标 | 想达成什么结果 | 完成事件处置并闭环 |
| 对象 | 操作规则、事件、任务、策略还是资产 | 事件、处置任务 |
| 动作 | 查看、配置、分配、处置、审核等 | 查看事件详情、执行处置 |
| 判断信息 | 用户凭什么做决定 | 风险等级、影响范围、处置时限 |
| 状态 | 操作前后如何变化 | 待处置 → 处置中 → 已处置 |
| 结果 | 成功、失败、部分成功分别是什么 | 处置成功闭环、处置失败退回 |
| 异常 | 权限不足、对象不适用、执行失败等 | 无处置权限、事件已过期 |

同一叙事中出现的多个动作、多个对象必须分别建模，不能只取主谓而丢动作与状态；重复出现的对象动作合并为同一任务，跨页面完成的动作记录其先后顺序（写入任务图的页面序列依赖，见 03-demo-page-decomposition.md 4.1）。

## 4. 内容分类规则

建模时把每条内容划分为四类，分类决定后续处理方式，也决定其在页面结构中的约束强度：

| 分类 | 含义 | 处理方式 | 示例 |
| --- | --- | --- | --- |
| 需求事实 | 需求中明确陈述的业务内容，是业务模型的真值 | 直接进入业务模型，作为页面字段、操作与状态的依据 | “用户需要处置事件” |
| 设计推导 | 从需求事实推导出的展示与组织方式 | 进入 designInferences，作为页面设计的推导依据，可优化 | “事件列表应展示风险等级和发生时间” |
| AI补齐 | 需求未提及、按展示层与常规交互补全的内容 | 进入 aiFillItems，明确标注，不得伪装为需求事实 | “处置失败时展示失败原因” |
| 产品规范补齐 | 需求未提及、但匹配 Product Design 声明为需求已建设对象/页面类型固有、必备或默认存在的能力 | 进入 productDesignCompleteness（source `product-design`），默认纳入范围；须登记可定位锚点，仅当用户明确不做或与需求业务事实冲突时剔除并记录原因 | “策略”类对象下默认包含的“资产适用规则检测” |
| 待确认问题 | 影响业务模型或页面结构且无法确定的缺失信息 | 进入 gaps，按第 7 节阻塞规则处理 | “处置是否支持批量操作” |

判定要点：描述“用户要做什么、对象是什么、状态怎么变”的是需求事实；描述“页面应如何展示、信息如何组织”的是设计推导；描述通用交互与反馈惯例的规范补齐属于 AI 补齐；只有用户能拍板且影响模型或结构的内容才进入待确认问题。

## 5. 来源标记与真值边界

requirementUnderstanding 中每项内容必须标记来源，禁止无来源内容混入业务模型：

- `requirement`：需求事实，来自 PRD、功能清单、Playbook、口述或用户确认。
- `product-design`：来自匹配 Product Design 产品设计规范的推导。
- `common-design`：来自 Common Design 通用设计规范的推导。
- `code`：来自已验证代码的推导（真实页面、组件、数据结构）。
- `ai-fill`：AI 合理补齐（仅限展示层与常规交互细节）。

真值边界：业务对象、核心动作、权限、状态流转、数量限制、业务规则、关键结果与异常属于业务事实，只能来自 `requirement` 或用户确认，AI 不得补造；展示层组织、通用交互、展示字段与常规反馈可由 AI 补齐（`ai-fill`）或按 Design Skill 推导（`product-design` / `common-design`）。来源优先级见 SKILL.md“设计知识调用与优先级 - 冲突原则”。

需求沉默边界：需求未提及不等于明确排除。匹配 Product Design 时，PD 声明为需求已建设对象/页面类型固有、必备或默认存在的能力（产品规范补齐项）默认纳入范围，标记 `product-design` 并登记可定位锚点；仅当用户明确表示不做或与需求业务事实冲突时剔除并记录原因。不得把需求未写当作排除 PD 固有能力（尤其业务规则类能力）的理由。

## 6. requirementUnderstanding 结构与字段说明

建模产物使用固定结构，字段与说明如下：

```yaml
requirementUnderstanding:
  status: resolved            # resolved 已解决 / needs_confirmation 有建议确认项 / blocked 有阻塞缺失
  inputType: mixed            # functional-list / narrative / mixed
  actors:                     # 角色清单，每项含角色名、岗位职责、核心任务
    - { name: "", role: "", tasks: [] }
  goals: []                   # 本次需求要达成的目标（用户视角）
  businessObjects: []         # 业务对象清单：对象名、生命周期状态集合、关键属性
  tasks:                      # 业务任务序列，是任务图与页面拆解的输入
    - id: T01                 # 稳定 ID，供后续任务图 / 页面职责引用
      actor: ""               # 执行角色
      trigger: ""             # 触发条件
      object: ""              # 操作的业务对象
      action: ""              # 动作（查看/配置/分配/处置/审核等）
      preconditions: []       # 前置条件
      requiredInformation: [] # 完成该动作所需的关键判断信息（页面展示的信息依据）
      outcome: ""             # 成功结果
      nextState: ""           # 操作后的对象状态
      exceptions: []          # 异常（权限不足/对象不适用/执行失败等）
  confirmedFacts: []          # 需求事实（来源 requirement / 用户确认）
  designInferences: []        # 设计推导（来源 product-design / common-design / code）
  aiFillItems: []             # AI 补齐项（来源 ai-fill），必须可被用户识别
  productDesignCompleteness:  # 产品规范补齐项（来源 product-design），匹配 Product Design 时必填
    - capability: ""          # PD 声明为固有/必备/默认存在的能力（需求未提及但默认纳入）
      appliesTo: ""           # 作用对象或页面类型（须为需求已建设的对象/页面类型）
      ref: ""                 # Product Design 文档原文锚点 <文档路径>#<章节/条目>
      decision: included      # included 默认纳入 / excluded（仅当用户明确不做或与需求业务事实冲突）
      reason: ""              # excluded 时必填排除原因
  gaps:                       # 缺失信息清单
    - question: ""            # 待确认问题（用户语言表述）
      impact: ""              # 影响范围（业务模型/权限/状态/数量限制/核心流程/页面结构）
      defaultAssumption: ""   # 当前默认假设
      blocking: true          # true=页面拆解前必须确认；false=带假设推进，随 Step 5 提出
```

状态判定：所有 gaps 已解决为 `resolved`；只存在 `blocking: false` 的建议确认项为 `needs_confirmation`；存在 `blocking: true` 的缺失为 `blocked`。该结构是内部推导产物，不写入 demo-spec JSON，也不进入 HTML 说明书；但影响页面拆解的结论（对象、任务、状态、判断信息）必须落实为页面字段、区块与状态规则。

## 7. 阻塞门禁与回流

进入页面类型与页面容器决策前必须核对门禁：业务对象、核心动作、关键结果或状态链路未确认时，不得进入页面类型和页面容器决策。

- `blocking: true` 的 gap（影响业务模型、权限、状态、数量限制或核心流程且无合理默认假设）：在页面拆解前以 Markdown 表格（序号｜待确认问题｜影响范围｜当前默认假设）输出为业务理解待确认问题并等待用户确认；用户回复后把结论更新进 requirementUnderstanding（confirmedFacts 或 tasks 调整），再进入页面拆解。若用户回复仍不完整，在同一表格中追加待确认问题并以表格一次性输出，不逐条交互式追问，直至满足准出条件。
- `blocking: false` 的 gap：记录默认假设与影响范围，带假设推进建模，随 Step 5 设计决策待确认问题一并提出。
- 回流：Step 4 页面拆解中发现业务模型理解错误或新缺失，按门禁返回本流程补齐 gaps 后再继续，不得带着未决业务模型强行拆页面。

## 8. 业务理解准出条件

只有同时满足以下条件，才允许进入页面拆解：

- 主要角色已明确；
- 核心业务对象已明确；
- 核心动作已明确；
- 用户完成任务所需的关键判断信息已明确，或有合理推导依据；
- 成功结果和主要异常已明确；
- 未解决的问题不会改变业务模型或页面结构。

任一条件不满足，先回流补齐（提出业务理解问题、补查需求资料或按来源规则补全），不得跳过准出条件直接输出页面类型与页面容器决策。

## 9. 示例

### 示例 1：功能清单式需求

输入为“事件管理：支持事件列表查询、事件详情查看、事件处置、处置记录查询”的功能清单。

提取结果（节选）：

```yaml
requirementUnderstanding:
  status: resolved
  inputType: functional-list
  businessObjects:
    - { name: "事件", states: ["待处置", "处置中", "已处置"], keyAttributes: ["风险等级", "发生时间", "影响范围"] }
  tasks:
    - id: T01
      actor: "安全运营人员"
      trigger: "进入事件管理"
      object: "事件"
      action: "查询与查看"
      requiredInformation: ["风险等级", "发生时间", "处置状态"]
      outcome: "定位需要处置的事件"
      nextState: "无状态变化"
      exceptions: []
    - id: T02
      actor: "安全运营人员"
      trigger: "选中待处置事件"
      object: "事件"
      action: "处置"
      requiredInformation: ["处置原因", "处置方式"]
      outcome: "事件闭环"
      nextState: "已处置"
      exceptions: ["无处置权限", "事件已过期"]
```

### 示例 2：叙事式 Playbook

输入为“运营人员收到事件告警后进入事件列表，筛选高危事件查看详情，确认影响范围后执行处置并填写处置原因，处置成功后事件闭环”。

按第 3 节逐段提取后得到：角色=运营人员；触发=收到事件告警；目标=完成处置闭环；对象=事件；动作序列=筛选高危事件、查看详情、确认影响范围、执行处置、填写处置原因；判断信息=风险等级与影响范围；状态=待处置→处置中→已处置；结果=处置成功闭环；异常=处置失败需退回。该叙事还隐含“处置需填写原因”的规则，若输入未说明是否必填、是否支持批量处置，则进入 gaps（默认假设：处置原因必填、暂不支持批量，随 Step 5 提出确认）。

### 示例 3：混合型需求与内容分类

输入同时含功能清单（“策略管理：列表、新建、编辑、删除”）与一段叙事（“管理员新建策略后先停用，验证无误再启用”）。

- 需求事实：策略支持新建、编辑、删除、停用、启用，停用/启用是显式状态操作，写入 businessObjects 状态集合与 tasks。
- 设计推导：策略列表应展示策略状态与最近操作时间；状态列适合用状态标签表达。
- AI补齐：删除高危策略前的二次确认弹窗、策略名称唯一性校验提示。
- 待确认问题：删除已启用策略时是否强制先停用（blocking=true，影响状态流转与页面结构）；新建表单是否按模板导入批量创建（blocking=false，带默认假设推进）。
